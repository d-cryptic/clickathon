## B · v2 engineering — real, reproduced, not worth destabilising v1 for

**B1 · Replace the per-run interval `DELETE` with tombstones.** Codex 003 §7.3.6, citing ClickHouse's
avoid-mutations guidance. Our measured cost is **1.4 s per publish run** — the dominant cost of a
small batch. Right in principle; not worth changing a pipeline that currently passes its gate.

**B2 · Cross-tier `generation_id` visibility.** `evidence/publish-visibility/` reproduced a reader
seeing the minute curve drop **−87.8% for up to 13.6 s** mid-publish, with hour and user tiers
lagging recovery by a further 3.8 s and 7.3 s. **A one-block correction fix is already prototyped**
(0 deviating samples, 79 ms swap) and handed off — that part may land in v1. The larger
`generation_id` work does not: naive gating was *rejected with a reason* (FINAL resolves before
WHERE on Replacing tiers, so an uncommitted row replaces-then-vanishes — worse than the problem).

**B3 · Provisional vs final bucket labelling.** Codex 003 §9: with an event-time watermark, buckets
older than `max_event_time − allowed_lateness` are final, newer ones provisional. We emit the
watermark and have never set `allowed_lateness` — see [`docs/DESIGN_DECISIONS.md`](docs/DESIGN_DECISIONS.md) §2,
where this is the one undecided decision of the organiser's four. **Blocked on a mentor answer, not on effort.**

**B4 · Skew and hotspot testing.** Codex 003 §10.3. Our scale ladder grows *uniformly*, which is the
easy case. Untested: one session with millions of events, most sessions starting in one minute (a
live event), one dimension value with enormous cardinality. The T2 cruel-data generator covers some
of this; a dedicated skew ladder does not exist.

**B5 · The publisher running for real on the graded database.** Proven byte-identical across four
tiers in scratch; `cc_publish_runs` on `sonyliv` is **empty**. Depends on A3.

**B6 · Langfuse emitter.** `internal/otelemit` was deliberately built so a second emitter could share
the same `trace_id` without a format change. Not built — the spec requires *one* of
ClickStack/Langfuse/LibreChat and ClickStack is done properly.

## C · Optional differentiators — the spec marks these optional, we chose ClickStack

**C1 · LLM + ClickStack alerting on concurrency decline.** `PROBLEM_STATEMENT.md:42`, explicitly
optional: *"detecting and alerting on concurrency decline — the asset ended, a system issue, or the
content is not engaging."* The better of the two options below, because it **deepens** our existing
mandated integration rather than adding a second shallow one.

**C2 · LibreChat + ClickHouse MCP conversational layer.** `PROBLEM_STATEMENT.md:75` and the suggested
demo's *"optionally, ask a follow-up question in chat."* The MCP server is preconfigured. Optional;
we already satisfy the integration requirement.
