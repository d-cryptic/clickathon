What the Stream? Phase 09

Stream Joins and Time Dependence

Why Stream Joins Are Different

Streams are unbounded, and a matching event may appear at any time. A stream join therefore needs to answer two questions that a bounded database query can often avoid:

  1. How much state should be retained while waiting for a match?
  2. Which version of changing reference data should be used?

Stream–Stream Join

Consider search ranking. One stream contains search-result impressions, and another contains clicks. We need to connect a click with the result impression that produced it.

A session ID alone may contain several searches and create incorrect many-to-many matches. The click should carry a unique query or result-impression identifier.

In a distributed application, a click may be processed before its matching search event because of network delay or retries. The processor maintains bounded state for both streams, indexed by the impression identifier. Whenever an event arrives, it stores the event and checks whether the other side has already arrived.

The window bounds how long unmatched events remain in state. It also defines when an unmatched search or click is considered complete enough to emit.

Stream–Table Join

Suppose a stream contains user activity with a user ID, and the output needs profile information for that user. Each activity event can be enriched by looking up the profile table.

A remote database lookup for every event may be slow and may overload the database. A common alternative is a local state store. The stream processor keeps a local profile view in memory or on disk and updates it through the profile database’s CDC stream.

A stream–table join may use an external lookup, although local replicated state is common. The key semantic choice is whether enrichment uses the latest profile at processing time or the profile version valid at the event’s timestamp.

Continuously Maintained Table–Table Join

Consider a social home timeline. A user sees posts from the accounts that the user follows. Reading every followed account at request time can be expensive, so the system can maintain a precomputed timeline.

The view reacts to both sides of the relationship:

  • When user B publishes a post, it is added to the timelines of users who follow B.
  • When B deletes a post, it is removed from those timelines.
  • When user A follows B, recent posts from B are added to A’s timeline.
  • When A unfollows B, B’s posts are removed from A’s timeline.

Because both posts and follow relationships change, the materialized view consumes changelogs for both tables. Conceptually, it is a continuously maintained table–table join.

Time Dependence and Determinism

Windowed stream–stream and changelog-based table–table joins require managed state. Stream–table joins may use managed local state or an external lookup.

Partitions preserve order within a partition, not across every input. We therefore need explicit semantics for changing data. Should an activity event join with the current profile, or with the profile that was valid when the activity occurred?

Deterministic recovery requires source offsets, consistent state snapshots, and versioned reference data when historical enrichment is required. Replaying the same recorded input can reproduce the same output when all state transitions and external dependencies are deterministic.

A stream join is not only a relationship between records. It is a relationship between records at a defined point in time.
