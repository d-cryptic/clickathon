# Codex Validation 003 — Deep algorithm, real-time, and scale audit

> **Historical terminology notice:** this audit predates upstream `c1e1c69`; there is no fixed private
> answer key or benchmark SQL set. Current correctness uses judge raw-event spot-checks.
>
> **Summary:** The interval-to-delta serving model is the right core design, but the complete system is not yet valid against judge spot-check or production failure semantics.
> A fixed 60-second reporting bucket and a 40/60-second heartbeat cadence are different clocks: derive event-time active intervals first, then intersect them with half-open minute buckets.
> Gaps must be calculated before dashboard reads; an incremental MV may mark touched sessions, but cannot exactly sessionize events across insert blocks because it sees only the new block.
> The current dirty-session finalizer and correction-by-diff algebra are eventually exact in the tested single-writer happy path, including shrink, dimension-change, user, and hour corrections.
> The shipped activity state machine remains semantically incomplete: it treats almost every event as liveness, ignores explicit background/foreground transitions, truncates milliseconds, and uses an unconfirmed 150-second gap plus 60-second tail.
> The publisher still has a consumed-before-claimed crash hole, timestamp identities, no fencing against concurrent writers, transient partial publication, a per-run DELETE mutation, and a 100x interval derivation that exceeded default memory.
> The contest-safe recommendation is to retain the model, harden the finalizer and boundary math, obtain the mentor answers below, and label recent results provisional until an event-time watermark makes them final.

## 1. Bottom-line verdict

The answer to “are all the algorithms and the design valid?” is **not fully**.

There are four different meanings of valid, and the repository currently reaches different levels on
each:

| Layer | Verdict | Reason |
|---|---:|---|
| Problem fit | **Strong** | Normalized active intervals plus minute deltas directly answer the upstream requirement without raw-history reads on dashboards. |
| Mathematical representation | **Strong with one boundary defect** | Signed interval deltas, hour clipping, correction-by-diff, and replaceable distinct-user buckets are sound; exact-end minute closure is currently inclusive rather than half-open. |
| Event semantics | **Unconfirmed / partial** | Private truth has not defined 40s versus 60s liveness, tail, pause/resume, background, error, end, same-time ordering, or dimension attribution. |
| Real-time implementation | **Eventually exact in the harness, not production-safe** | The tested finalizer converges, but its claim protocol is not atomic or multi-writer safe and readers can observe intermediate phases. |
| 100x scale | **Serving passes; derivation partial** | Compact deltas scale well, but the all-history `groupArray` session derivation failed at default 100x memory settings. |
| Live deployment | **Not a coherent proof** | Validation 002 found mixed live model generations and an installed-but-idle publisher. |

The design should **not** be discarded. Its durable core is correct:

```text
append-only raw events
        -> deterministic active intervals
        -> signed minute-boundary deltas
        -> running concurrency curve
        -> minute/hour/day peak and time-weighted average
```

The work remaining is chiefly to make the event definition exact and the incremental protocol safe.

## 2. The two clocks must never be mixed

There are two independent time concepts:

1. **Reporting grain:** the dashboard reports fixed 60-second buckets, normally
   `[M, M + 60s)`.
2. **Evidence cadence:** a player may emit an authoritative liveness signal every 40 seconds, every
   60 seconds, or from more than one source.

A 60-second report bucket does not imply a 60-second heartbeat timeout. A 40-second heartbeat does
not imply 40-second report buckets.

The order of operations must be:

```text
ordered events
  -> active event-time ranges at millisecond precision
  -> overlap those ranges with fixed 60-second reporting buckets
  -> aggregate session or user membership
```

Do not round events to minutes before reconstructing state. Do not choose the inactivity timeout
from the report grain.

### 2.1 If both 40s and 60s signals are authoritative

The correct general form is a lease per signal class `c`:

```text
expiry_c = last_valid_signal_c + timeout_c
session_liveness_expiry = max(expiry_c)       -- if either stream is sufficient evidence
```

If the organiser defines tolerance in missed beats, derive `timeout_c` from that stream's cadence and
jitter budget. If it defines a single fixed timeout, use that fixed duration. These are different
contracts and cannot be inferred from the CSV.

If all streams are required rather than alternatives, `max` is wrong; the rule could be `min` or a
named canonical stream. That is why the mentor must answer which event values are authoritative.

Current `GAP_S = 150` has no uniform missed-beat meaning:

| Cadence | 150-second gap represents |
|---:|---:|
| 40 seconds | 3.75 cadences |
| 60 seconds | 2.5 cadences |

Current `TAIL_S = 60` is 1.5 cadences for a 40-second stream and one cadence for a 60-second stream.
It is a policy, not a cadence-derived truth.

## 3. Foreground and background, precisely

**Foreground** means the application is visible/interactive enough that playback may count as
watching. **Background** means the application is not the active visible application, or playback has
otherwise moved into a state the organiser says must not count.

Foreground alone is insufficient. A foreground app may still be paused, ended, errored, or silent.
The useful predicate is:

```text
active(t) = foreground(t)
         AND playing(t)
         AND not_ended(t)
         AND liveness_lease_valid(t)
```

Unknown is not the same as true. Because `AppBackgrounded` and `AppForegrounded` are not guaranteed,
their absence cannot prove either state. But when an explicit negative event is present, ignoring it
also needs a justification.

### 3.1 Required independent state axes

Keep these axes independent; overlapping states are normal:

| Axis | Example states |
|---|---|
| Visibility | unknown, foreground, background |
| Playback | unknown, playing, paused |
| Lifecycle | not-started, open, ended, errored |
| Liveness | valid until timestamp, expired |

Examples:

- `resume` while still backgrounded must not activate the session.
- `AppForegrounded` while still paused must not activate it.
- Heartbeats received while paused may refresh telemetry but must not count as watching if pause is
  excluded.
- A later play/foreground event after `VideoSessionEnd` needs a defined reopen/new-epoch rule.

### 3.2 Recommended event behavior, pending mentor confirmation

This is a conservative implementation proposal, not a claim about private truth:

| Event | Proposed state effect |
|---|---|
| `VideoSessionStart` | Establish session epoch; do not count until play/liveness evidence if those are required. |
| `VideoPlay` | Set playing; renew liveness; open only if not explicitly backgrounded/ended. |
| Authoritative heartbeat | Renew its signal-class expiry; do not override pause/background/end. |
| `pause` | Set paused and close active interval immediately. |
| `resume` | Clear paused; reopen only if visibility/lifecycle/liveness permit. |
| `AppBackgrounded` | Set background and close immediately when present. |
| `AppForegrounded` | Clear background; reopen only with the organiser-approved positive evidence. |
| `VideoSessionEnd` | Close immediately; later events follow an explicit reopen/new-session rule. |
| `VideoError` | Close, retain, or mark unknown only after organiser confirmation; never silently treat every error as positive liveness. |
| Unknown event | Store and alert; do not silently grant liveness unless the event class is allow-listed. |

The current SQL does not implement this table. It uses all event timestamps for gap runs, subtracts
only exact lowercase `pause`/`resume` windows, and uses `VideoSessionEnd` only for `is_open`.

## 4. Correct interval and minute mathematics

Use half-open active intervals `[s, e)`. For a minute bucket `[M, M + 60s)`, membership is:

```text
s < M + 60s AND e > M
```

This handles every boundary without special cases.

### 4.1 Delta encoding

For any-positive-overlap minute semantics:

```text
open_minute  = floor_to_minute(s)
close_minute = ceil_to_minute(e)

+1 at open_minute
-1 at close_minute
```

`ceil_to_minute(e)` must return `e` when `e` is already an exact minute boundary. The current code
always uses `floor(e) + 60s`, so an interval ending exactly at `10:01:00` is counted in
`[10:01:00, 10:02:00)`. Validation 002 measured 518 affected intervals in the then-live table.

Zero-length `[s, s)` intervals cover no minute and must be dropped. Reversed ranges after clipping
must fail loudly or be quarantined.

### 4.2 Hour clipping

Re-opening a continuing interval at each hour and omitting a close outside that hour is valid. It
makes every hour's running sum self-contained, so arbitrary range reads need at most:

- stored full-hour peak/integral rows; and
- minute deltas for the two partial edge hours.

Per `schema-pk-cardinality-order` and the repository conventions, this is a good serving compromise.
It also makes day peak `max(hour_peak)` valid **only for the same already-aggregated filter level**.

### 4.3 Peak and average invariants

- Apply all requested filters and reconstruct the curve **before** taking `max`.
- Never add or maximize peaks from different dimension buckets to infer a union.
- Average must be `integral(concurrency over time) / requested duration`, including zero-concurrency
  periods, unless the benchmark explicitly defines a different denominator.
- Distinct users are not the sum of distinct users across sessions or dimensions.

## 5. Where gap calculation belongs

### 5.1 Dashboard read time — reject as the serving path

Reading raw events, grouping every session, sorting event history, finding gaps, subtracting pauses,
and expanding overlap on every dashboard query can be correct eventually. It is not a valid serving
design at the stated scale because cost grows with retained history and repeats for every reader.

Keep this path only as the independent reconciliation oracle.

### 5.2 Direct incremental materialized view — reject for exact sessionization

An incremental ClickHouse MV is an insert trigger over the newly inserted block. It does not
automatically have the prior event from a session when that event was inserted in an earlier block.
The first row of a block therefore cannot decide its preceding gap, pause state, or background state
without external state/recomputation.

This is consistent with the official
[incremental materialized view documentation](https://clickhouse.com/docs/concepts/features/materialized-views/incremental-materialized-view)
and vendored `query-mv-incremental`: use an incremental MV for transformations that are correct from
the inserted block, not for hidden cross-block state.

The repository uses the MV correctly when `mv_session_dirty` records which sessions an insert
touched. It would use it incorrectly if the MV itself claimed to finalize exact active intervals.

### 5.3 Refreshable materialized view — valid only for a bounded hot window

A refreshable MV reruns its query on a schedule. It can periodically replace a recent hot window and
is a reasonable ClickHouse-only fallback when:

- bounded staleness is accepted;
- event lateness is bounded;
- the hot-window query finishes comfortably inside the refresh interval; and
- older late events have a separate correction path.

It is not automatically incremental and is not a good answer if a full hot-window recomputation every
few seconds approaches the schedule period. See the official
[refreshable materialized view documentation](https://clickhouse.com/docs/concepts/features/materialized-views/refreshable-materialized-view)
and vendored `query-mv-refreshable`.

### 5.4 Dirty-session micro-batch finalizer — chosen ClickHouse-native path

The strongest contest-compatible path is:

```text
ev_raw INSERT
  -> incremental MV writes durable dirty-session/change rows
  -> one fenced finalizer claims a micro-batch
  -> ClickHouse re-derives only affected session state/intervals
  -> one signed old-to-new correction is appended
  -> touched user/hour buckets are replaced
  -> committed generation becomes visible
```

This keeps concurrency computation in ClickHouse while using a small service only for coordination.
It is the right place to calculate gaps at scale.

## 6. Solution-option validity matrix

| Option | Correctness | Freshness | Scale | Verdict |
|---|---:|---:|---:|---|
| Raw scan and gap calculation per dashboard query | Eventual truth possible | Current | O(history) per query | **Oracle only** |
| Persist every session-minute | Exact if semantics are exact | Good | O(active duration), large writes/storage | **Validation/small scale only** |
| Direct incremental MV sessionization | Wrong across insert blocks | Excellent | Cheap | **Reject** |
| Stateless heartbeat-to-minute `uniqExact` leases | Exact for a gap-only monotone model | Excellent | High write fan-out | **Comparison/provisional only; cannot retract pause/background** |
| Refreshable MV over recent window | Exact inside recomputed window | Periodic | Window-query dependent | **Fallback** |
| Current dirty-session finalizer plus correction-by-diff | Eventual exactness proven under chosen semantics | Seconds | Session/window bounded | **Keep and harden** |
| Two-tier provisional + sealed model | Can label uncertainty honestly | Best | More operational complexity | **Useful only if sub-minute “now” is required** |
| External stateful stream processor | Strong production event-time semantics | Excellent | Strong | **Production alternative, but core computation outside ClickHouse conflicts with the contest's strict wording** |

## 7. Audit of the current implementation at `51ef49f`

### 7.1 What is valid and should remain

1. **Normalized intervals rather than session spans.** Necessary to exclude inactivity.
2. **Signed minute deltas rather than history-wide per-minute rows.** Storage/write growth follows
   interval boundaries, not active duration.
3. **Hour-clipped deltas.** Makes each hour independently queryable and pre-aggregatable.
4. **Correction-by-diff.** `-old + new` is exact algebra for late pause, resume, heartbeat, end, and
   dimension changes when old/new derivations are deterministic.
5. **`Int64` corrective measures.** Required; unsigned negative corrections silently wrap.
6. **`ReplacingMergeTree(build_version)` for current interval versions.** Corrects both interval
   growth and shrink; versioning by `interval_end` was invalid.
7. **Dirty-session MV.** Correct use of an incremental MV: it indexes arrivals rather than pretending
   to know cross-block state.
8. **Replaceable user/hour buckets.** ADR 0016 closes the old set-union retraction and stale-hour
   problems. The harness covers shrink and dimension flip on all four tiers.
9. **Deterministic dimension voting instead of `any()`.** Rebuild reproducibility is essential.
10. **Query-time content dictionary.** Avoids fact rewrites when metadata changes, subject to the
    documented refresh delay and negative-key layout.

### 7.2 What is not semantically valid yet

1. **All events drive liveness.** `VideoError`, background events, seeks, resize, telemetry bursts,
   and unknown future events can bridge a gap and receive tail credit.
2. **Explicit background is not a close transition.** Missing pairs justify not requiring a pair;
   they do not prove that an observed background should be ignored.
3. **`VideoSessionEnd` is not terminal.** It changes `is_open` but the run can receive tail credit and
   later events. Events after end need an explicit reopen/session-epoch rule.
4. **Millisecond precision is discarded.** `toUnixTimestamp(event_timestamp)` converts
   `DateTime64(3)` to whole seconds. The `>=` resume workaround avoids one symptom but does not define
   ordering for simultaneous pause/play/background/end events.
5. **Cadence inference is weak.** The p99 of all mixed heartbeat payloads is not a contract for which
   source proves playback liveness.
6. **Tail and gap are unconfirmed.** The sensitivity results show they materially move the answer.
7. **Exact minute end is inclusive.** This conflicts with standard half-open overlap.
8. **Dimension attribution is a product choice.** Dominant-per-interval and earlier-interval-wins
   during minute merging are deterministic, but not necessarily private truth.
9. **Unknown events fail open.** An unseen event value silently extends activity instead of being
   surfaced for semantic review.

### 7.3 What is not operationally safe yet

1. **Consumed-before-claimed crash hole.** `cc_publish_consumed` is written before the `claimed`
   phase marker. A crash between them leaves no in-flight run to resume but hides the dirty marking
   from the next run.
2. **No single-writer fencing.** Two finalizers can both observe no in-flight run, claim the same
   sessions, and append duplicate corrections.
3. **Timestamp is used as insert identity.** `DateTime64(3)` can collide across independent inserts;
   settle time lowers probability but does not create uniqueness.
4. **`run_id` is wall-clock milliseconds.** Concurrent processes can collide and clock movement is
   not a durable sequence.
5. **Readers see intermediate phases.** After old deltas are negated and before new deltas are
   emitted, minute concurrency can temporarily drop. Hour and user tiers are updated still later.
6. **Mutation per run.** `DELETE FROM session_intervals` removes vanished old keys. Official
   [ClickHouse mutation guidance](https://clickhouse.com/docs/concepts/best-practices/avoid-mutations)
   recommends avoiding frequent mutations; append a tombstone/version instead.
7. **Dedup token assumptions differ by engine.** Cloud shared/replicated behavior does not prove
   local non-replicated replay safety, and dedup windows are finite.
8. **Seven-day queue TTL can delete unprocessed work.** Retention must exceed the maximum outage with
   a hard alert and a rebuild path.
9. **No atomic cross-tier generation.** Minute, hour, and user queries can observe different
   publication points during a run.
10. **Install-after-history is idle by design.** A bootstrap/backfill marker is required when the
    publisher is added to a populated service.

## 8. Hardening the finalizer without redesigning everything

### 8.1 Durable identity and claim protocol

Replace ingest-time identity with a durable ordered change identity, preferably source
partition/offset or an ingestion batch UUID plus row/block sequence.

One safe sequence is:

1. Acquire a single-writer lease with a monotonically increasing fencing token.
2. Insert a run record with a UUID, frozen lower/upper change cursor, and `claimed` status.
3. Materialize batch membership idempotently from that frozen cursor.
4. Never mark input changes consumed before a durable resumable run exists.
5. Build old intervals, new intervals, tombstones, and signed delta diff in staging.
6. Append the complete `-old + new` correction in one insert block.
7. Replace touched hour/user buckets under the same generation.
8. Commit the generation, then advance the input cursor.

Use a tuple cursor `(source_offset)` or `(ingest_time, change_uuid)`, never a timestamp alone.

### 8.2 Remove interval DELETEs

Store append-only interval versions keyed by stable logical interval ID with:

- `version`;
- `is_deleted`; and
- `run_id`/fencing token.

When a late event merges two prior intervals, append the merged interval and a tombstone for the
vanished key. Read the latest non-deleted version. This follows the vendored
`decision-late-arriving-upserts` guidance and avoids one mutation per publish run.

### 8.3 Make publication visibility coherent

At minimum, put both negative and positive minute corrections in one insert block so readers do not
observe a negative-only phase.

For cross-tier coherence, add `generation_id` and expose only committed generations, or make the
dashboard explicitly label each tier's publish cursor. A ClickHouse-wide multi-table transaction
must not be assumed.

### 8.4 Preserve a full rebuild

Incremental correctness must always have a deterministic repair path:

- rebuild from raw into new versioned tables;
- reconcile against an independent raw oracle;
- atomically switch an indirection/view to the new generation;
- retain the previous generation briefly for rollback.

## 9. Real-time truth requires provisional and final states

There is an information-theoretic trade-off after the latest heartbeat. Suppose the last signal was
at `t` and the next expected one has not arrived:

- Counting until the full gap timeout avoids undercounting a delayed next beat but temporarily
  overcounts a viewer who actually stopped.
- Counting only a shorter tail avoids inventing viewers but temporarily undercounts a delayed beat;
  a later arrival retroactively corrects history.

No database design can know which world is true before enough event time passes.

Use an event-time watermark:

```text
final_before = max_event_time_seen - allowed_lateness
```

- Buckets older than `final_before` are **final**, except for explicit very-late corrections.
- Newer buckets are **provisional** and may move.
- Measure both event-time watermark lag and ingest-to-publish lag.

If the judges require only eventual benchmark truth, the current finalizer pattern is sufficient
after hardening. If they require an exact processing-time “right now,” ask how provisional truth is
scored; exactness before the timeout is impossible without an explicit source active flag.

## 10. 100x scale design

The serving model is not the first bottleneck. The measured 100x run reached about 89.85 million
events and 1.086 million sessions; compact deltas reconciled, while interval derivation hit
`Code: 241` under default memory settings.

### 10.1 Why the current batch derivation hits memory

`sql/30_build_intervals.sql` builds full arrays of timestamps and dimension tuples for every session
in one large aggregation. Memory grows with all simultaneously open aggregation states, and one hot
session can also build an unusually large array.

External aggregation spill makes the benchmark finish but does not make full-history rebuilds a
real-time architecture.

### 10.2 Scale-safe processing pattern

- Batch inserts, normally 10K–100K rows, and use async inserts for unavoidable small producers, per
  vendored `insert-batch-size` and `insert-async-small-batches`.
- Partition raw storage by event date/time for retention and bulk operations, not by session ID.
- Process dirty sessions in bounded micro-batches and group only those sessions.
- Add a session/time access path. A full projection previously reduced a one-session read 12.8x but
  added about 91% raw-table storage. Official
  [projections](https://clickhouse.com/docs/concepts/features/projections/projections) now support
  `_part_offset`-based lightweight projections on compatible versions; benchmark that alternative on
  Cloud 26.2 instead of assuming the old storage multiplier is permanent.
- Compact closed session state so the normal path does not reread unlimited history.
- Keep a slow-path full session rederive for arrivals older than the compacted horizon.
- Bound batch size by events/bytes, not only number of sessions; one pathological session can dominate.
- Apply backpressure when publish runtime approaches the batch interval.
- Never let queue TTL expire pending work silently.

### 10.3 Skew and hotspots

Test these separately from average scale:

- one session with millions of events;
- one user with many concurrent sessions;
- a live event where most sessions start in one minute;
- one extremely high-cardinality dimension value per event;
- a burst of late pauses that all shrink the same busy hour;
- a replayed full source batch;
- an outage longer than the normal lateness window.

## 11. Complete edge-case register

### 11.1 Event ordering and identity

- Duplicate event with same payload and same source identity.
- Two legitimate events with identical payload/timestamp but different source offsets.
- Same-millisecond pause/resume or background/foreground.
- Multiple state events at the same timestamp with no sequence number.
- Out-of-order play before start; end before start; event timestamp before `session_start_epoch`.
- Multiple starts/ends and events after end.
- Session ID reused across days or devices.
- Future-dated timestamp, invalid epoch, or clock rollback.

### 11.2 State combinations

- Pause then background; resume while backgrounded.
- Background then pause; foreground while paused.
- Unmatched background, foreground, pause, or resume.
- Repeated pause/pause and resume/resume.
- Heartbeats during pause or background.
- Buffering, seek, ad, casting, download, or error signals while playback is not watchable.
- App killed with no end/background event.
- Explicit end followed by a delayed older heartbeat versus a genuine later restart.

### 11.3 Interval and bucket boundaries

- Start exactly on a minute/hour/day boundary.
- End exactly on a minute/hour/day boundary.
- Start and end inside one minute.
- Zero-length interval.
- Pause/resume inside the same millisecond, second, or minute.
- Interval crossing UTC/IST day boundary and daylight-saving zones if non-UTC zones are allowed.
- Query range starting/ending inside an hour.
- Empty query range and a range containing only zero-concurrency minutes.

### 11.4 Late data and replay

- Late heartbeat extends a tail.
- Late pause shrinks an interval.
- Late resume expands an interval.
- Late event bridges two runs and deletes one prior logical interval.
- Late dimension event changes attribution without moving time.
- Event older than queue TTL, raw TTL, watermark, or compacted session state.
- Processor crash before claim, after claim, after each write phase, and after commit before ack.
- Two finalizers start together.
- Dedup token expires before replay.

### 11.5 Dimensions and user counting

- Dimension changes mid-interval or mid-minute.
- Unknown/new dimension column or value.
- Case/spelling aliases and sentinel values.
- Missing content key and later catalog arrival.
- One title mapped to multiple content IDs.
- One user active in two sessions, contents, platforms, or countries in the same minute.
- Query requesting a union of dimension buckets; never sum their peaks or distinct users.

### 11.6 Operations

- MV installed after historical data.
- MV target insert failure.
- Raw mutation/partition drop that does not retrigger the MV.
- Parts explosion from small inserts.
- Mutation backlog from per-run DELETE.
- `FINAL` cost as version history grows.
- Dictionary refresh lag or failed reload.
- Cross-generation dashboard queries during publication or rebuild.

## 13. Validation plan required before a full-valid claim

### 13.1 Semantic golden tests

Create tiny hand-auditable fixtures for every mentor decision, with millisecond timestamps and exact
expected intervals/minutes. Include all state combinations and boundary cases in section 11.

These fixtures must not reuse the production derivation as their expected-value generator.

### 13.2 Differential/property tests

For randomly generated sessions:

- compare the optimized state machine to a simple reference interpreter;
- compare interval expansion to delta running sums;
- verify splitting/merging/reordering the same input batches does not change final output;
- verify duplicate source identities are idempotent;
- verify `old + (-old + new) = new` for arbitrary interval/dimension changes;
- verify session counts are non-negative and user counts never exceed session counts at the same
  filter grain.

### 13.3 Failure-injection tests

Kill the finalizer at every line between claim and commit, then restart and compare every serving tier
to a clean rebuild. Start two finalizers simultaneously. Repeat after dedup windows and across a queue
partition/TTL boundary.

The current harness proves data-shape convergence; it does not prove these coordination failures.

### 13.4 Scale gates

At 1x, 10x, and 100x capture:

- ingest rows/s and part count;
- dirty queue rows and unique sessions;
- per-phase rows/bytes read, memory, spill, and latency;
- correction rows appended per source event;
- `FINAL` and mutation costs;
- filtered minute/hour/day query latency and bytes read;
- reconciliation mismatch count;
- watermark/publish lag under steady state and burst recovery.

## 14. Recommended delivery decision

For the hackathon, present this as a **ClickHouse-native incremental compaction design**:

```text
                         +---------------- raw reconciliation oracle
                         |
events -> ev_raw -> dirty-session MV -> fenced micro-batch finalizer
                                      -> versioned interval ledger
                                      -> signed minute deltas
                                      -> replaceable user/hour aggregates
                                      -> minute/hour/day serving views
                                      -> ClickStack lag + correctness telemetry
```

Implement/fix in this order:

1. Obtain mentor decisions for cadence/liveness, explicit transitions, boundaries, and lateness.
2. Preserve milliseconds and implement the explicit multi-axis state machine.
3. Fix half-open close-minute arithmetic and add boundary fixtures.
4. Replace timestamp cursor/identity and close the claim/concurrency crash holes.
5. Emit correction pairs atomically and replace interval DELETE with tombstones.
6. Add committed generation visibility across tiers.
7. Add a session access projection/state compaction and rerun 100x under production settings.
8. Rebuild all live tiers from one commit, run full reconciliation/benchmark evidence, then enable the
   continuous publisher with backpressure and alerts.

Until steps 1–4 are complete, the honest claim is:

> The repository has a strong, compact, eventually consistent interval-to-delta implementation that
> is exact under its chosen semantics and tested correction shapes. It is not yet proven to match the
> organiser's foreground definition or to survive every crash/concurrent-writer edge case.
