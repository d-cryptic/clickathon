# Codex Validation 004 — Preprocessing boundary and research-branch adjudication

> **Summary:** Keep the system ClickHouse-first; do not introduce a Python/pandas pipeline that owns cleaning, sessionization, foreground state, heartbeat gaps, deduplication, or concurrency.
> Retain a thin Python or Go ingestion adapter for header inspection, source identity, batching, retries, and transport, then add an immutable all-`String` ClickHouse landing table before the typed `ev_raw` boundary.
> ClickHouse can cast, flag, quarantine, normalize, carry unknown dimensions, and pre-aggregate, but an incremental MV cannot reconstruct cross-block session state or retract an old interval after a late bridging event; the dirty-session finalizer remains necessary.
> The current preprocessing design is close but not unseen-safe: one typed value can reject the whole insert, and `v_ev_model_input` is not wired into both the interval builder and reconciliation gate.
> The `feat/problem-space-research` branch remains a source of useful ideas, not mergeable code: its source-contract gate, writer-safety doctrine, correction algebra, watermark model, and peak non-additivity are valid; its wholesale architecture and sessions-only bet are not.

**Validated:** 2026-08-02 against repository commit `9c26918`. This is an architecture and repository
evidence review. It made no runtime or database changes.

---

## 1. Decision

The system needs **preprocessing**, but it does not need a general-purpose preprocessing service.

The recommended boundary is:

```text
CSV / file / stream
        │
        ▼
thin ingestion adapter (Python or Go)
  header · source identity · batches · retries · transport
        │
        ▼
ev_landing (recommended; not implemented)
  every source value as String + ingest metadata
        │
        ├── cast/classify in ClickHouse SQL
        │
        ├── accepted ─────────────────────► ev_raw
        ├── unusable ─────────────────────► ev_quarantine
        └── suspicious but usable ────────► flags/metrics
                                                │
                                                ▼
                                MV marks affected sessions dirty
                                                │
                                                ▼
                                   stateful session finalizer
                              full history · gaps · pauses · corrections
                                                │
                                                ▼
                                  hour-clipped signed deltas
                                                │
                                                ▼
                                  minute/user/hour serving tiers
```

The boundary is deliberately thin. Python and Go are suitable transport and orchestration tools;
they must not become a second implementation of the business model.

### 1.1 What belongs in the adapter

- Parse and validate the CSV header before sending rows.
- Detect new, missing, renamed, duplicated, or malformed column names.
- Attach `ingest_batch_id`, source filename/object key, source checksum, row number and ingestion
  timestamp where available.
- Batch, compress, retry and send rows idempotently.
- Fail loudly on structurally malformed CSV that cannot be represented as a row.
- Report a batch outcome; never silently skip a row.

The current loader already uses Python's standard `csv` module for header inspection in
[`tools/load.sh`](../../tools/load.sh). That is appropriate. Rewriting it as Go may improve packaging
if it becomes a long-running service, but it does not improve the data model and is not currently
necessary. Pandas adds memory, serialization, and semantic-drift risk without solving a problem this
workload has.

### 1.2 What must not belong in the adapter

- Foreground/background or play/pause state transitions.
- Heartbeat gap or tail decisions.
- Session-window merging.
- Minute boundary membership.
- Business-level deduplication.
- Dimension attribution.
- User or session concurrency.
- Silent trimming, repair, defaulting, or deletion.

If either Python or Go implements these rules, the repository acquires two definitions of an active
viewer: one before ClickHouse and one in reconciliation. Both can be individually green while
disagreeing with each other and the private ground truth.

## 2. Why ClickHouse is sufficient for most preprocessing

ClickHouse can own the deterministic, inspectable transformations that this dataset needs:

- format parsing and schema-directed reads;
- `String` normalization and UTF-8 checks;
- typed casts using `accurateCastOrNull`;
- accepted/quarantine classification;
- reason and warning flags;
- `Map` or `JSON` storage for evolving attributes;
- append-only raw storage;
- insert-time transformations and additive rollups;
- query-time normalization for filter values;
- dictionaries or query-time joins for content enrichment.

Per the vendored [`insert-batch-size`](../../.claude/skills/vendor/clickhouse-best-practices/rules/insert-batch-size.md)
rule and ClickHouse's [official insert guidance](https://clickhouse.com/docs/concepts/best-practices/selecting-an-insert-strategy),
producers should prefer batched synchronous inserts, ideally 10,000–100,000 rows. Per
[`insert-async-small-batches`](../../.claude/skills/vendor/clickhouse-best-practices/rules/insert-async-small-batches.md),
use `async_insert=1, wait_for_async_insert=1` when clients cannot form adequate batches. Do not use
fire-and-forget ingestion for correctness-scored data.

The important official limitation is also explicit: if any row in an insert query has a parsing or
type error, the entire payload is rejected. Therefore "ClickHouse-native" does **not** mean inserting
hostile CSV directly into the final typed table. It means landing representable source values as
strings and performing tolerant, observable type conversion inside ClickHouse.

### 2.1 Recommended tolerant-load contract

Add an immutable landing table whose source fields are `String`, with source metadata sufficient to
locate the original row. Then classify each landing batch with ClickHouse SQL:

```text
accurateCastOrNull succeeds + identity/time usable  -> ev_raw
accurateCastOrNull fails                             -> ev_quarantine(type_mismatch)
identity or timestamp unusable                       -> ev_quarantine(named_reason)
usable but suspicious                                -> ev_raw + q_flags
clean                                                -> ev_raw
```

This should be batch-addressable and idempotent. A manifest or batch status must make it possible to
prove that every landing row reached exactly one terminal disposition. The landing table—not a local
DataFrame—is the recoverable source when a classification rule changes.

The policy in [ADR 0025](../adr/0025-hostile-input-quarantine-over-rejection.md) is otherwise sound:

- reject nothing by a hidden business rule;
- quarantine only rows the model cannot use correctly;
- keep and count suspicious but usable rows;
- preserve raw bytes/values;
- normalize filter values on read rather than rewriting history.

### 2.2 Flat unknown dimensions: retain `extra Map`

[ADR 0024](../adr/0024-carry-unknown-filter-columns-in-an-extra-map.md) correctly stores unforeseen
flat CSV columns in `extra Map(LowCardinality(String), String)`. It was measured at +0.48% compressed
for empty maps and +3.6% for two populated keys, with unchanged load latency at the supplied scale.

This gives a new dimension survivability and immediate raw queryability. It does **not** make the
dimension magically available in an aggregate that was keyed without it:

- if it is derived from an existing key, query-time normalization may serve it immediately;
- if it is independent, raw recomputation is the no-migration path;
- if it becomes a hot filter, promote it to a typed column/key and rebuild the relevant tier.

ClickHouse's production `JSON` type is a valid future choice for nested or truly semi-structured
payloads; see the [official JSON documentation](https://clickhouse.com/docs/reference/data-types/newjson).
The current input is flat CSV, so replacing the measured `Map` with JSON now would add migration and
type-inference surface without a demonstrated benefit.

### 2.3 Content enrichment must respect MV trigger direction

Per vendored [`decision-join-enrichment`](../../.claude/skills/vendor/clickhouse-architecture-advisor/rules/decision-join-enrichment.md),
an incremental MV is triggered by inserts to its source/left table. A later change to the right-hand
`content_dim` table does not retroactively update already materialized event rows.

For this system, keep `content_id` in the compact serving facts and either:

- join/dictionary-resolve title, video type and category at query time; or
- explicitly rebuild/backfill affected serving results when content metadata changes.

Do not assume that placing the catalog join inside an MV makes catalog corrections propagate.

## 3. Why an incremental MV is not the sessionizer

Per vendored [`query-mv-incremental`](../../.claude/skills/vendor/clickhouse-best-practices/rules/query-mv-incremental.md)
and ClickHouse's [incremental MV documentation](https://clickhouse.com/docs/concepts/features/materialized-views/incremental-materialized-view),
the MV query receives the newly inserted block, not an automatically consistent view of all prior
rows in the source table.

Consider:

```text
10:00 heartbeat
10:04 heartbeat       -> initially two runs under a bounded-gap rule
10:02 late heartbeat  -> bridges them into one run
```

Processing only the 10:02 block cannot delete the two previous interval outputs and replace them with
the merged output. This is the late-arriving-upsert problem described by vendored
[`decision-late-arriving-upserts`](../../.claude/skills/vendor/clickhouse-architecture-advisor/rules/decision-late-arriving-upserts.md).

The current division of responsibility is correct:

1. An MV records which session changed.
2. The finalizer reads that session's complete event-time history.
3. It deterministically derives the replacement intervals.
4. It emits `new - old` signed correction deltas, including zero/tombstone effects.
5. The serving tables merge those additive corrections.

Gaps are therefore calculated during finalization/publication, not on every dashboard read. This
makes correction cost proportional to touched sessions and query cost proportional to compact
serving data rather than raw history.

Per [`insert-mutation-avoid-update`](../../.claude/skills/vendor/clickhouse-best-practices/rules/insert-mutation-avoid-update.md),
append-only versioned/corrective rows are preferred to repeated in-place mutations on the hot path.
The remaining per-run DELETE noted elsewhere in the repository is an operational follow-up, not a
reason to move the model into Python.

## 4. Current repository: what is valid and what is incomplete

| Area | Verdict | Evidence / qualification |
|---|---:|---|
| Header drift handling | **Valid** | New columns are announced and carried; missing required columns refuse before load. |
| Unknown flat dimensions | **Valid with tier boundary** | Queryable from `extra`; independent dimensions require raw recompute or tier promotion. |
| Quarantine policy | **Valid design, partially integrated** | Measured classifier and recovery exist; typed batch failure remains. |
| Source-contract validation | **Valid and adopted** | Read-only FAIL/WARN/INFO gate exists as ADR 0026. |
| Interval/delta representation | **Valid core** | Compact, hour-clipped signed deltas avoid raw per-minute event expansion. |
| Late correction algebra | **Valid core** | Dirty-session re-derivation plus correction-by-diff is the right mathematical form. |
| MVs as complete state engine | **Invalid** | They see inserted blocks, not automatically complete session history. |
| Foreground/heartbeat semantics | **Unconfirmed** | Multiple plausible readings differ materially and private truth is unavailable. |
| Lateness/finality policy | **Incomplete** | Corrections accept arbitrary lateness, but no chosen allowed-lateness contract exists. |
| External stateful stream processor | **Not currently justified** | More infrastructure without evidence that the finalizer misses its SLA. |

### 4.1 Two mandatory preprocessing corrections

1. **Tolerant landing.** The current typed `input()` path can reject a whole batch because one value
   cannot parse. Stage source values as strings and route null casts to a named quarantine reason.
2. **Wire the clean boundary atomically.** `sql/30_build_intervals.sql` and three reads in
   `sql/90_reconcile.sql` still use `ev_raw`, while `v_ev_model_input` exists but is not enforced.
   Change the builder and reconciliation gate together, never one without the other. The current
   exposure is documented in [`PREPROCESSING.md`](../PREPROCESSING.md).

The source-contract gate from [ADR 0026](../adr/0026-source-contract-gate-read-only-verdict-before-trust.md)
should continue to run after landing/load and before any model output is trusted. It reports protocol
drift; it must not also clean or mutate rows.

## 5. Increased requirements: where each kind belongs

More requirements do not automatically imply another service. Route each requirement to the layer
that owns its invariant:

| New requirement | Correct owner |
|---|---|
| New flat filter column | Header gate + `extra Map`; promote only when it becomes a hot serving key |
| Nested/semi-structured payload | ClickHouse `JSON`, with typed hints for frequently queried paths |
| Missing required column | Loader refusal; never silently default identity or event time |
| New event/event-type vocabulary | Source-contract gate + explicit semantics decision; never silently grant liveness |
| 40-second and 60-second heartbeat sources | Event-time state model parameters; not preprocessing and not synthetic row generation |
| Late/out-of-order heartbeat | Dirty-session finalizer and correction-by-diff |
| Changed content metadata | Query-time dictionary/join or explicit backfill; not an assumed MV cascade |
| New high-frequency filter cuboid | Deliberate serving-key/schema change plus rebuild and reconciliation |
| Dashboard freshness/finality | Event-time watermark + provisional/final status |
| PII that legally cannot land raw | Upstream redaction/tokenization before ClickHouse; this is a genuine external requirement |

The 40-second versus 60-second issue is especially important. Reporting buckets are fixed 60-second
minutes, while heartbeat cadence is evidence about liveness. Preserve actual event timestamps and
parameterize/test `GAP_S` and `TAIL_S`; do not create artificial heartbeats in preprocessing. The
current `150 s / 60 s` policy is a measured hedge, not externally confirmed truth. Event lateness
also remains open; see [`DESIGN_DECISIONS.md`](../DESIGN_DECISIONS.md).

## 6. `feat/problem-space-research`: feature-by-feature verdict

The prior [design bake-off](../design-bakeoff.md) reached the correct high-level conclusion: reject
wholesale adoption and reuse selected ideas against the current architecture. The branch evolved the
superseded `sql/10_intervals.sql`, collides with later ADR numbers, lacks the current user/hour/day
tiers, and does not have comparable Cloud/convergence evidence.

### 6.1 Valid and already adopted or reimplemented

| Research item | Verdict |
|---|---|
| Hour-clipped signed-delta ledger | **Keep.** It is the right compact serving representation and is already current. |
| Dirty-session re-derivation and correction-by-diff | **Keep.** Same durable mathematics as the incumbent finalizer. |
| Source-contract acceptance/reporting gate | **Keep.** Reimplemented against current dev as ADR 0026. |
| Single-writer publication doctrine | **Keep.** Current ADR 0019 is stronger than a local `mkdir` lock. |
| Fresh deduplication tokens for replayable phases | **Keep.** Required for repeatability and already used by the publisher. |
| "Filtered peak is not additive" | **Keep.** A stored maximum is reusable only for its exact filter cuboid. |
| Independent semantic implementation | **Keep as evidence.** It reveals model risk; it is not private ground truth. |

### 6.2 Valid production roadmap, not required preprocessing

| Research item | When it is useful |
|---|---|
| Event time + ingestion time + watermark | Required for an honest provisional/final contract under continuous streaming. |
| `event_id` | Exact producer-level retry deduplication. |
| `session_incarnation_id` | Prevent old state from poisoning a reused session identifier. |
| `player_instance_id` and `state_scope` | Define which playback a background/pause transition governs. |
| `producer_sequence` | Deterministic ordering of tied state transitions. |
| source partition/offset and `ingest_batch_id` | Replay checkpoints and proof of what a run consumed. |
| `schema_version` | Explicit event-contract evolution and dead-letter routing. |
| Session projection | Worth keeping when finalizer point-lookup benchmarks justify its storage cost. |
| Model-version hash | Cheap, useful evidence that two runs used the same semantics. |
| Proof-carrying result envelope | Useful for observability: value, status, watermark, model version and reconcile run. |
| Bitemporal `--as-of-run` replay | Valuable for audit/demo; lower priority than correctness and unseen execution. |

These are source-contract and operational improvements. They do not justify a Python transformation
service. Most require better identifiers from the producer; no downstream cleaner can reconstruct an
event ID or player scope that was never emitted.

### 6.3 Conditional, not default

| Research item | Decision condition |
|---|---|
| Bounded exact mutable tail | Add only if required freshness is materially below the current publisher cadence. |
| External Flink/Beam/Dataflow sessionizer | Add only when measured live keyed state, correction backlog, lateness, or freshness exceeds the ClickHouse finalizer's SLA. |
| RisingWave/Materialize-style differential state | Consider only if SQL-first continuously retractable joins become a central requirement. |
| Native JSON instead of `extra Map` | Adopt when incoming data becomes nested/semi-structured, not merely because flat columns increase. |

### 6.4 Reject or hold for mentor confirmation

| Research item | Reason |
|---|---|
| Merge the branch wholesale | Superseded files, colliding ADRs, missing tiers and weaker verification. |
| Sessions-only metric bet | The problem and current system require protection for both session and user concurrency. |
| Local filesystem lock as production lease | Does not coordinate separate hosts; current ClickHouse-backed lease is stronger. |
| Remove the session-independent baseline | Deletes a required comparison and an important model-bias detector. |
| Treat bounded exact tail as an always-on second architecture | Redundant unless a stricter freshness target demonstrates the need. |
| Split intervals on every dimension drift without a contract | Can double-count or ambiguously attribute session-minute membership. |
| Treat fail-closed foreground state as proven | App background/foreground events are explicitly not guaranteed; organizer semantics must decide. |
| Treat half-open boundary/state-gated output as ground truth | Defensible alternatives, but still alternatives until compared with organizer truth. |

The research state-gated implementation measured approximately **10.9% less foreground watch time**
than the incumbent. Both implementations reconcile against their own conventions, so that delta is a
mentor/private-truth question, not evidence that the lower or higher number is correct.

## 7. When an external preprocessing or stream-processing layer becomes justified

Do not add one because the statement gained clauses. Add one only when a requirement cannot be
satisfied reliably inside the current boundary:

1. **Durable multi-producer replay and backpressure dominate ingestion.** Put Kafka/Pub/Sub or a
   managed ingestion connector before ClickHouse; keep ClickHouse as raw and serving storage.
2. **Stateful correction misses a measured SLA.** If active keyed state, out-of-order volume or
   correction backlog makes the finalizer miss freshness/resource targets, move sessionization to
   Beam/Dataflow or Flink keyed state and keep the same signed-delta contract downstream.
3. **Sub-second freshness is required.** The scheduled finalizer is no longer the right trigger;
   benchmark a real stream processor rather than a home-grown Python loop.
4. **Data may not legally land raw.** Perform mandatory PII redaction/tokenization upstream.
5. **The source uses a proprietary format or external API enrichment.** Parse/enrich before
   ClickHouse, while preserving source identity and deterministic replay.

"More columns," "more event values," and "40/60-second cadence" do not meet these conditions.

## 8. Final architecture verdict

| Decision | Verdict |
|---|---:|
| Thin Python/Go adapter | **Yes** |
| Pandas/general Python transformation pipeline | **No** |
| Immutable all-String ClickHouse landing table | **Yes — next ingestion hardening** |
| ClickHouse-native casts, flags, quarantine and normalization | **Yes** |
| `extra Map` for unforeseen flat dimensions | **Yes** |
| Incremental MV for stateless transforms/dirty-session marking | **Yes** |
| Incremental MV as the complete session state machine | **No** |
| Stateful finalizer for gaps, pauses, foreground and late correction | **Yes** |
| Read-time raw sessionization for dashboard queries | **No** |
| External stateful stream processor now | **No, absent a measured trigger** |

The expanded design is valid once tolerant landing and clean-view wiring are completed. The largest
remaining risk is not the absence of Python; it is unresolved business semantics—what grants
liveness, how background/pause transitions scope, how 40/60-second signals combine, where minute
membership closes, and when an event-time bucket becomes final.
