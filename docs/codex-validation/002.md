# Codex Validation 002 — Canonical dataset-contract audit

> **Historical terminology notice:** this audit predates upstream `c1e1c69`. Read “private ground
> truth” below as the organiser's raw-event spot-check interpretation; there is no fixed answer key.

> **Summary:** Validated the canonical SonyLIV raw/content data dictionary against repository `dev` at `45dd01c` and the live `sonyliv` Cloud database on 2026-08-01.
> Every declared source column is typed and ingested, all seven raw filter dimensions reach the accurate interval/delta model, and all current event content IDs resolve to catalog rows.
> That is not the same as complete contract support: most event types are stored but not interpreted as state transitions, `session_start_epoch` is unused, and dimensions are collapsed to one dominant value per interval.
> User, hour/day, window, content, and dashboard paths expose different dimension subsets; arbitrary new dimensions require coordinated code/schema changes and are not dynamic.
> Live Cloud is internally split across model generations: minute peak 2,887, hour peak 2,917, user peak 2,845; the installed publisher has never committed a run and normalization is not deployed.
> Therefore the system handles the delivered columns structurally, but it is not yet proven to handle every field's business meaning, every filter/grain combination, or judge spot-check semantics.

## 1. Question and answer

The question is whether the implementation handles everything promised by
[`docs/upstream/dataset_details.md`](../upstream/dataset_details.md): identifiers, timestamps, event
semantics, user/session concurrency, seven raw filter dimensions, three content filter dimensions,
the real-time content lookup, and growth in the number of dimensions.

The answer is **no, not completely**.

The correct distinction is:

| Claim | Verdict |
|---|---:|
| Every canonical CSV column is represented in ClickHouse | **Yes** |
| Every column is parsed with an appropriate type | **Yes, for the delivered files** |
| Every event type affects concurrency according to its business meaning | **No** |
| Session and total user concurrency exist | **Yes, under the repository's chosen semantics** |
| Every named dimension is present somewhere downstream | **Yes** |
| Every dimension works uniformly at session/user and minute/hour/day grain | **No** |
| Arbitrary combinations of the seven raw dimensions can be queried | **Yes at minute drilldown; custom SQL elsewhere** |
| Title/video type/category can be combined freely with every raw dimension | **Not through one shipped serving interface** |
| New dimensions are automatically accepted | **No** |
| New dimensions preserve bounded delta-table growth after code changes | **Yes** |
| Live Cloud matches the current repository's claimed model generation | **No** |

This document supersedes the dataset-specific portions of
[`docs/codex-validation/001.md`](001.md) when the two differ. Validation 001 was taken before the
hosted dashboard, scale, and later runtime changes now present on `dev`.

## 3. Canonical raw-field coverage

All 13 raw columns exist in `ev_raw` and are loaded in canonical CSV order. The schema is in
`sql/00_schema.sql`; conversion is in `tools/load.sh`.

| Canonical column | Stored type | Used by the model | Contract status |
|---|---|---|---:|
| `video_session_id` | `String` | Grouping identity for intervals, deltas, session concurrency | **Supported** |
| `user_id` | `String` | Dominant user per interval; `uniqExact` user concurrency | **Partial** |
| `content_id` | `Int64` | Interval/delta dimension and catalog key | **Supported with attribution caveat** |
| `event_type` | `LowCardinality(String)` | Only `VideoSessionEnd` is explicitly interpreted in accurate derivation | **Partial** |
| `event` | `LowCardinality(String)` | Exact lowercase `pause` and `resume`; every other value is generic activity | **Partial** |
| `event_timestamp` | `DateTime64(3)` | Primary time source for runs, pauses, dimensions, partitions | **Supported** |
| `platform` | `LowCardinality(String)` | Dominant per interval; delta/filter dimension | **Supported with attribution caveat** |
| `app_version` | `LowCardinality(String)` | Dominant per interval; delta/filter dimension | **Supported with normalization caveat** |
| `country` | `LowCardinality(String)` | Dominant per interval; delta/filter dimension | **Structurally supported, unseen untested** |
| `audio_language` | `LowCardinality(String)` | Dominant per interval; delta/filter dimension | **Partial: raw spelling and attribution** |
| `subtitle_language` | `LowCardinality(String)` | Dominant per interval; delta/filter dimension | **Partial: sentinel/dedup attribution** |
| `player_version` | `LowCardinality(String)` | Dominant per interval; delta/filter dimension | **Supported with attribution caveat** |
| `session_start_epoch` | `DateTime64(3)` | Loaded only; not used in derivation or serving | **Stored, not modeled** |

### 3.1 Types and loading

The loader reads both source timestamp columns as `UInt64`, divides epoch milliseconds by 1,000, and
converts them to `DateTime64(3)`. On the delivered file this preserves the expected millisecond value.

`content_id` is correctly signed `Int64`. This matters because the content file contains the planted
negative key `-987654322`; an unsigned type would reject it and could reject an unseen raw event using
the same shape.

Raw strings are not constrained to a fixed enum. That makes ingestion forward-compatible with new
values, but it also means an unknown event type silently becomes a generic activity timestamp rather
than failing for semantic review.

### 3.2 Identifiers are not as stable as their names imply

The delivered file contains:

| Condition | Sessions |
|---|---:|
| More than one `user_id` | 120 |
| More than one `content_id` | 1 |
| More than one `platform` | 95 |
| More than one `country` | 0 |

The implementation resolves these by selecting the dominant value within each active interval,
tie-broken by value for determinism. This avoids nondeterministic `any()`, but it is a product policy,
not a fact stated by the canonical dictionary.

For user-level answers, a session that changes `user_id` can be attributed to one dominant user for
an entire interval. For content/platform filters, a change during an interval is similarly collapsed.

### 3.3 `session_start_epoch`

On this file, every session has one stable `session_start_epoch`, and it matches its
`VideoSessionStart.event_timestamp` exactly: zero mismatching sessions and maximum difference 0 ms.

The derivation nevertheless ignores the column and obtains run starts from the minimum/gap-split
event timestamp. This happens to be harmless on the delivered file. It is not a validated invariant
for an unseen file with missing, duplicated, delayed, or contradictory start events.

## 4. Canonical event-type coverage

The canonical page lists seven event types. Their actual treatment is:

| Event type | Rows | Accurate interval behavior | Verdict |
|---|---:|---|---:|
| `VideoSessionStart` | 10,880 | Generic timestamp in the run; does not explicitly open/bound state | **Partial** |
| `VideoPlay` | 10,883 | Generic timestamp; also included by the stateless MV | **Partial** |
| `VideoHeartbeat` | 843,600 | Every sub-event timestamp renews the gap-based run; `pause`/`resume` get extra handling | **Partial by design** |
| `AppBackgrounded` | 14,700 | Generic timestamp; does not explicitly close active state | **Not semantically implemented** |
| `AppForegrounded` | 14,321 | Generic timestamp; does not explicitly reopen active state | **Not semantically implemented** |
| `VideoSessionEnd` | 10,881 | Generic timestamp plus `countIf(...)=0` for `is_open`; does not force a terminal boundary | **Partial** |
| `VideoError` | 293 | Generic timestamp; can renew a run and receive tail credit | **Not semantically defined** |

### 4.1 What the SQL actually does

The accurate derivation creates one sorted timestamp array from **all** rows in a session. A gap over
150 seconds splits the array. It separately builds arrays only for exact `event = 'pause'` and
`event = 'resume'`, and uses `VideoSessionEnd` only to set `is_open`.

There is no branch on `AppBackgrounded`, `AppForegrounded`, `VideoSessionStart`, `VideoPlay`, or
`VideoError`.

This conflicts with ADR 0001 and the interval-math guide, which say background/foreground events are
corroborating signals that may close an interval earlier. The implementation uses them only because
their timestamps happen to participate in gap arithmetic.

### 4.2 Background/foreground semantics

The decision not to **pair** background with foreground is defensible:

- The source says both are not guaranteed.
- Counts are 14,700 versus 14,321.
- 418 sessions background and never return.

That does not imply an explicit `AppBackgrounded` should be ignored when present. Under the current
SQL it can be treated as proof of recent activity and can receive 60 seconds of tail grace. Whether
private truth expects immediate inactivity at that event is unresolved.

### 4.3 Start/end semantics

`VideoSessionEnd` is intentionally not treated as final because 239 sessions emit 802 later events,
up to 2,081 seconds after an end. That protects late/out-of-order data, but it means the system has no
explicit rule for whether an end terminates playback until a later play/foreground signal.

Likewise, `VideoSessionStart` does not exclusively establish the start; any earlier row would become
part of the run. Current data does not expose that case.

### 4.4 `VideoError`

The dictionary identifies a playback error but does not define whether it terminates active viewing.
The system has made an implicit choice: it is another timestamp. Because it can extend a gap run and
receive tail grace, calling it "ignored" would be inaccurate.

### 4.5 Heartbeat cadence

The canonical page says heartbeats are currently passed every minute. The delivered file instead has
41 `VideoHeartbeat.event` values. Three major telemetry streams tick at roughly 40 seconds, while
others occur in bursts or at different periods.

The shipped policy uses:

- `GAP_S = 150`
- `TAIL_S = 60`

Those are 3.75 and 1.5 times the observed 40-second cadence, not "2.5 missed one-minute beats" and
"one cadence." The data supports rejecting a literal one-minute assumption, but the private truth's
policy remains unknown.

## 5. The `event` payload

`VideoHeartbeat` contains 41 distinct event names. The accurate model interprets only exact lowercase
`pause` and `resume`:

- `pause`: 27,340 rows
- `resume`: 31,780 rows

Pause-like values such as `speed-pause`, `AdPause`, `speed-resume`, `AdResume`, and
`download_resumed` are intentionally not matched. This avoids false classification, but it also
means the event vocabulary is a private-truth dependency.

The remaining values—buffering, seek, resize, bandwidth, language-change, ad, casting, download,
quality, and other events—affect concurrency only by renewing the all-event gap sequence and by
participating in the dominant dimension vote.

The source says `event` is useful for tracking a particular event. The raw table preserves that
ability, but the serving model exposes no event-level analytical rollups besides the implicit
pause/resume semantics.

## 6. Duplicate and repeated-event handling

Current raw data contains:

| Duplicate measure | Result |
|---|---:|
| Byte-identical duplicate rows beyond the first | 4,209 |
| Repeated `(session, timestamp, event_type, event)` keys | 4,210 |
| Duplicate-key groups | 3,413 |
| Groups whose remaining payload conflicts | 1 |

There is no explicit event deduplication in the accurate derivation; duplicated timestamps enter the
arrays. Exact duplicates generally do not move interval boundaries or total concurrency. The one
conflicting group changes `subtitle_language`, so dedup is not guaranteed inert at filter grain.

The loader prevents accidentally loading the same complete CSV twice, but that guard is not event
deduplication and does not remove repeated records inside one file or across intentional append loads.

## 7. Minute-boundary semantics

The interval expansion counts every minute from `toStartOfMinute(interval_start)` through
`toStartOfMinute(interval_end)`, inclusive. The delta path closes at the minute after the interval's
end minute.

On the current live interval table:

- 518 intervals end exactly on a minute boundary.
- 506 sessions are affected.

Under half-open overlap semantics, an interval ending at `10:01:00` has no overlap with the minute
`[10:01:00,10:02:00)`. The shipped model counts it. Both the serving layer and its reconciliation
truth share the inclusive rule, so a green gate cannot settle the definition.

## 8. Raw filter-dimension coverage

Seven raw dimensions are stored in `session_intervals` and `cc_minute_delta`:

1. `content_id`
2. `platform`
3. `country`
4. `app_version`
5. `audio_language`
6. `subtitle_language`
7. `player_version`

### 8.1 What is genuinely supported

- `cc_minute_delta` can be filtered by any combination of all seven columns with custom SQL.
- `v_cc_by_platform`, `v_cc_by_country`, `v_cc_by_app_version`,
  `v_cc_by_audio_language`, `v_cc_by_subtitle_language`, and
  `v_cc_by_player_version` provide one-dimension curves for hosted dashboards.
- `v_concurrency_minute` provides platform/country/content-ID combinations.
- `v_session_minutes` carries `video_session_id`, `user_id`, all seven raw dimensions, and title,
  allowing distinct-session or distinct-user minute drilldowns under arbitrary raw-dimension filters.

### 8.2 What is not uniform

| Serving path | Dimensions directly exposed |
|---|---|
| `cc_minute_delta` | All seven raw dimensions |
| `v_concurrency_minute` | Platform, country, content ID |
| `cc_hour_agg` / hour/day views | Platform, country, content ID only |
| `cc_user_minute` / user views | Platform, country, content ID only |
| Rolling/tumbling/range views | Platform, country, content ID only |
| `v_session_minutes` | All seven raw dimensions plus title; not video type/category |
| Stateless comparison | Platform, country, content ID only |

Therefore a benchmark asking for user concurrency by audio language, day peak by app version, or a
rolling window by subtitle language does not have the same prebuilt path as a platform/content query.
It can be reconstructed with custom SQL or the chart expansion, but "all dimensions are supported"
overstates the uniformity.

### 8.3 Per-interval attribution

The model does not split an active interval when a dimension changes. It selects the most frequent
value observed within that interval and uses a deterministic value tie-break.

Advantages:

- One session contributes at most one tuple in a merged viewer-minute.
- Total concurrency remains additive.
- Rebuilds are deterministic.

Costs:

- A viewer changing audio, subtitle, app, platform, user, or content during one interval is not
  attributed according to exact time of change.
- Direct multi-bucket occupancy and the single-tuple serving model can disagree on filtered cells.
- Dedup can change which value wins without changing total concurrency.

This is a defensible modeling policy, not a fact supplied by the canonical dictionary.

### 8.4 Country is effectively untested

The delivered raw file has exactly one country value. Schema, sorting, grouping, and views include
country, but no current-data test can expose cross-country attribution or filtering errors.

## 9. Dimension-value normalization

The raw file contains spelling/case families such as `hin`, `HIN`, `hin-hindi`, and `hin-Hindi`.
Literal equality treats these as different filter values. `sql/15_normalise.sql` defines query-time
normalization functions and drift views while preserving raw storage.

At validation time, live Cloud had none of:

- `norm_case`
- `norm_lang`
- `norm_version`
- `norm_app_version`
- `lang_class`
- `v_cc_minute_delta_norm`
- `v_concurrency_minute_audio_norm`
- `v_dimension_drift`
- `v_dimension_drift_summary`

The code is wired into the current batch build script, but it has not been applied to the live
database. Hosted per-language views therefore operate on raw spellings.

Normalization itself contains unresolved product choices: for example, whether `non` means an off
state, whether blank/unknown values combine, and whether language subtags should collapse. The raw
view remains necessary until the benchmark convention is known.

## 10. User-level concurrency

The canonical dictionary explicitly distinguishes session-level and user-level concurrency. The
repository correctly uses `uniqExact` user sets rather than session deltas, because a user can hold
multiple sessions simultaneously.

Limitations:

1. `cc_user_minute` is keyed only by platform, country, content ID, and minute.
2. It cannot answer user concurrency by app/audio/subtitle/player or content metadata without a
   separate path.
3. Its set union can add membership but cannot retract a user from a superseded minute/dimension
   bucket after an interval shrinks or is relabeled.
4. `v_session_minutes` can calculate distinct users under arbitrary raw filters, but it is a
   per-minute expansion for dashboard drilldown, not the compact serving tier.
5. Live user peak 2,845 does not correspond to either live interval distinct-user count at the
   documented peak (2,815) or the newer repository claim (2,844), confirming tier drift.

## 11. Content dataset and real-time join

All four content columns are correctly represented:

| Canonical column | Stored/served behavior | Verdict |
|---|---|---:|
| `content_id` | Signed primary lookup key | **Supported** |
| `title` | Query-time dictionary value; can name multiple assets | **Partial** |
| `video_type` | Query-time dictionary value; blank bucket preserved | **Supported with policy caveat** |
| `category` | Query-time dictionary value | **Supported** |

### 11.1 Current join integrity

- 33,464 content rows and 33,464 unique content IDs.
- 3,357 content IDs appear in raw events.
- 0 orphan content IDs and 0 orphan raw events.
- Missing future keys are preserved as `(unknown)` rather than dropped.
- Blank catalog values are labeled `(blank)` rather than merged with missing keys.

### 11.2 Title is not an asset key

The catalog contains 30,508 distinct titles for 33,464 content IDs:

- 2,773 titles map to more than one content ID.
- 1,418 such titles span multiple categories.
- 198 span multiple video types.

`v_concurrency_minute_title` intentionally groups all assets sharing a title. Its
`catalog_content_ids` column exposes the ambiguity, but a caller can still mistakenly quote the row
as one asset. `v_concurrency_minute_content` is the safer per-ID path.

### 11.3 "Joined in real time"

The implementation enriches delta results through a ClickHouse dictionary at query time. The
dictionary reload lifetime is 300–600 seconds, so:

- No fact-table rewrite is required for catalog metadata.
- A catalog update is not guaranteed to appear immediately; it may remain cached for up to roughly
  ten minutes.
- The content views are query-time enriched but not transactionally joined to the event insert.

`v_session_minutes` hard-codes `sonyliv.dict_content`, making that chart-only view non-portable to an
unseen scratch database without rewriting or recreating it there.

### 11.4 Cross-dimension combinations

Prebuilt title/video-type/category views collapse all raw dimensions except time. `v_session_minutes`
has title plus all seven raw columns, but lacks video type and category. A query such as
"distinct users by audio language and video type" therefore needs custom dictionary lookup over the
session-minute expansion or a new view; it is not a uniform shipped serving shape.

## 12. Additional-dimension extensibility

The canonical note says the solution should work if dimensions increase. Two separate questions must
not be conflated.

### 12.1 Storage-growth property: good

The delta table emits at most one open and one close per merged run/hour. Adding dimensions changes
which rows coalesce; it does not create a Cartesian minute-by-dimension explosion. The measured
seven-dimension row count remains below the open+close ceiling, including the 100x synthetic test.

### 12.2 Schema extensibility: manual

Adding a new source dimension currently requires coordinated edits to:

1. `ev_raw` schema.
2. CSV `input()` schema and `INSERT` projection.
3. `session_intervals` schema.
4. The interval `dim_events` tuple, extraction arrays, and dominant-value vote.
5. `cc_minute_delta` schema and sort key.
6. The delta fold tuple, indexes, projections, and final select.
7. Normalization/drift logic if values need canonicalization.
8. User/hour/window/content serving shapes if they must support it.
9. Incremental publisher templating and scratch schemas.
10. Reconcile, truncation, scale, dashboard, and unseen-day tests.

There is no `Map`/dynamic dimension representation and no schema registry. The system is
fixed-schema extensible with bounded delta growth; it does not automatically handle an unknown new
column.

## 13. Scale validation

The repository includes measured 1x, 10x, and 100x audience tests. At 100x:

- Approximately 89.85 million events and 1.086 million sessions were generated.
- The reconciliation gate passed on 6,799 minutes after the model completed.
- Delta and hour-tier serving remained fast and approximately linear.
- The default interval derivation failed with ClickHouse `Code: 241` memory exhaustion.
- It completed only with external aggregation spill/reduced threads, using several GiB of memory.

The scale evidence validates the delta representation better than it validates the end-to-end
pipeline. The first failure is session-array derivation memory, not dimension row count, dictionary
memory, or too many parts.

The evidence was generated from an older model baseline and records dirty SQL/tools at generation
time. It is valuable shape evidence, not a byte-for-byte certification of current `45dd01c`.

### 14.3 Normalization deployment

Normalization is committed and invoked by the current batch-build script, but absent from live
Cloud. Code capability and runtime capability therefore differ.

## 15. Documentation inconsistencies affecting confidence

Current repository documents disagree on the dataset contract:

- `WALKTHROUGH.md` says all ten filter dimensions are done.
- `TODOS.md` still says normalization is built but not wired, although `build-model.sh` now applies it.
- Live Cloud shows that it is wired in code but not deployed.
- `checklist.md` retains an older table saying only three of ten dimensions survive and content
  concurrency is missing.
- `sql/80_content.sql` comments still describe `any(content_id)` per session, while current interval

- Scale evidence uses an older 2,887 baseline and explicitly says SQL/tools were dirty.
- Live serving currently mixes the older 2,887 minute tier with the newer 2,917 hour tier.

These conflicts do not automatically invalidate the SQL, but they prevent a reviewer from treating
one narrative document as confirmed current state.

## 16. What can be claimed safely

The following statement is supported:

> The repository ingests every canonical raw/content column with suitable types. Its accurate model
> reconstructs gap- and pause-aware session intervals, carries seven raw dimensions into a compact
> minute-delta table, supports current content lookup by ID/title/video type/category, and provides
> distinct-session and distinct-user minute drilldowns. The current file has complete content-ID
> coverage, and the delta representation remains bounded as dimension cardinality grows.

## 17. What cannot be claimed safely

The following statement is not supported:

> Every canonical event type is interpreted according to foreground playback state; every named or
> future dimension works uniformly for session/user and minute/hour/day/window queries; all filtered
> values are normalized in production; all tiers update continuously and atomically; live Cloud is
> on one reconciled model generation; or the chosen semantics match judge spot-check expectations.

## 18. Contract gaps requiring closure

Before marking the canonical dataset contract complete, the following must have explicit decisions
and evidence:

1. Define whether an observed `AppBackgrounded` immediately closes active viewing and what events can
   reopen it, without relying on guaranteed pairs.
2. Define `VideoSessionStart`, `VideoPlay`, `VideoSessionEnd`, and `VideoError` state transitions,
   including events arriving after an end.
3. Decide whether `session_start_epoch` is authoritative, a consistency check, or deliberately
   ignored; validate unseen contradictions.
4. Confirm heartbeat cadence, gap, tail, unclosed-pause, overloaded-resume, and exact minute-boundary
   semantics with the organiser/private truth.
5. Define duplicate identity and filter-payload conflict resolution.
6. Define timed dimension attribution when values change within an active interval.
7. Provide one tested query contract covering every required dimension at session/user and
   minute/hour/day grain, rather than relying on different partial views.
8. Decide raw versus normalized filter semantics and deploy the chosen query-time objects.
9. Treat title as a label and content ID as the asset key in benchmark inputs/outputs.
10. Decide whether future dimensions require explicit migrations or a dynamic representation; state
    that contract honestly.
11. Rebuild/reconcile every live tier from one commit and dataset, then prevent cross-generation
    serving.
12. Exercise the deployed incremental publisher on real appended blocks and validate user/hour/day
    downstream convergence, crash recovery, and single-writer enforcement.

## 19. Final verdict

The system is substantially better than "three dimensions and a heartbeat count." It correctly
preserves the canonical data, implements a sophisticated gap-plus-pause interval model, exposes all
seven raw dimensions somewhere in the query surface, joins content metadata, and has measured scale
evidence.

It does **not** yet handle "everything as per the data dictionary" in the strong sense. Structural
coverage is high; semantic, grain, deployment, and extensibility coverage remain partial. Most
urgently, the live database currently serves mutually inconsistent minute, user, and hour answers,
so no broad completeness claim is valid until the runtime is brought back to one reconciled model
generation.
