01 — the problem

A session being open is not a person watching

The data gives you when a session started, when it ended, and a heartbeat roughly every minute in between. The tempting reading is that a session is "on" from its first event to its last. That reading is wrong, and it is wrong in one direction: it always over-counts.

Someone backgrounds the app to answer a message. Someone pauses and walks away. Someone loses signal in a lift. The session object survives all three. The viewer does not.

This is the whole insight, and it is why one signal is not enough. Heartbeat gaps catch backgrounding, because heartbeats effectively stop — 0.047/min against 4.72/min. But heartbeats survive a pause at 0.756/min. A model built on gaps alone counts every paused viewer as watching, silently, and looks perfectly healthy while doing it. Pause must be excluded explicitly.

03 — the algorithm

From a pile of events to an active interval

Per session, ordered by time. Six steps, each of which exists because some real session breaks without it.

Where this model is deliberately not clever. It does not treat explicit AppBackgrounded as a hard state transition. We measured the alternative rather than assuming: it moves the peak by 17 out of 23,324, and the gate turns out to be 92.4% redundant with the gap rule — it removes 17 and adds 2 back. The same measurement found something larger we had not been looking for: tail credit past a terminal background is worth −202. Both are disclosed, neither is silently applied.
04 — the model

Hour-clipped signed deltas

An interval does not become a row per minute. It becomes exactly two numbers: +1 when it opens, −1 when it closes. Concurrency at any minute is the running sum. That is small, exact, and filterable — but a naive running sum has a fatal property: it depends on every row before it, forever.

So each interval is clipped to every hour it touches. Each hour's running sum starts from zero and is absolute. A query for 14:00 reads one hour of deltas, not the history of the dataset.

Two things about these numbers that are easy to get wrong

Peak is not summable

Per-platform peaks occur at different minutes. Summing the 19 of them gives 24,025 (+3.01%); taking the maximum gives 7,163 (−69.29%). Both wrong, opposite directions. The true peak is 23,324 and must be computed on the union.

Average is time-weighted

Not a mean of per-minute values. The integral is 81,621,960 concurrency-seconds over 86,400 s → 944.6986. Averaging only the 795 active minutes gives 1,711.15 — a different question, printed separately rather than blended.

Users are a separate exact tier

uniqExact, never uniq — an HLL sketch carries 1–2% error against an exact key, unacceptable for a headline. Peak users 22,279, and it lands one minute before the session peak.

The peak minute is softer than the peak

11:17 leads 11:16 by six viewers. Every alternative semantic reading we tested reverses that ordering. The value is robust; the minute is worth quoting with care.

Determinism, across two very different machines

The full result matrix was executed twice — once on a local container, once on ClickHouse Cloud. 26 of 27 queries returned byte-identical output across two ClickHouse versions, two engine families, and 3 versus 10 threads. Cloud is ~7× slower and reads the same rows, so the difference is host, not model.

07 — the limits

What we would tell a judge before they found it

Country is a dead filter

country is the constant 'india' in all 7,000,000 rows. The requirement that filters alter the curve is met by 11 of 12. We kept the control visible and said so.

Backgrounded-state exposure

Bounded at 0.72% of counted hours and 0.91% at peak, measured both ways. Shipped as the reconciled reading, not the flattering one.

Session identity

159 session IDs carry more than one start epoch; 303 carry more than one user. Grouping on the session alone can merge incarnations.

Landing tier on Cloud

The hosted build was transferred already-typed, so the lossless-landing proof (7,000,000 = 7,000,000 + 0 rejects) stands on the local build, not this one.

The reason any of this is checkable. The gate recomputes concurrency from raw events with an independent implementation and refuses to pass on any disagreement — 3,201,716 minutes compared, 0 mismatched. It fails on zero rows too, so a gate that cannot see its data cannot pass by silence. Every number in this document survives that check, or is labelled as not having been through it.
