01 — THE PROBLEMTwo words do all the damage

Given session start/end events, player heartbeats and playback-state markers, answer "how many people were actually watching at minute M" — for any minute, any dimension filter, at dashboard latency, while sessions are still arriving. Everything hard lives in actually watching.

1.1 · The naive model, and where it breaks

The obvious approach is interval overlap: a session spans [start, end], and concurrency at minute M is how many spans cover M. That counts a phone sitting in someone's pocket with the app open. It counts a paused player. It counts a session whose heartbeat died twenty minutes ago.

The sample data says this is not a rounding error. All 10,866 sessions in the provided file contain at least one AppBackgrounded event. Backgrounding is the median session, not an edge case. Span-based concurrency is therefore systematically inflated, and every ad-load, capacity and content decision downstream inherits that inflation. That is the entire reason the problem exists.

1.2 · The two collapses

Correctness is only half the problem. The statement names both scaling failures explicitly, and both are worth understanding precisely because the fix is chosen by eliminating them.

1.3 · What the data actually looks like

The provided file is 905,559 events across 10,866 sessions, spanning 2026-07-14 to 2026-07-26 (≈11.8 days). The event mix matters because it dictates which signals are trustworthy.

02 — THE ARITHMETICThe delta model and its three sharp edges

For each active interval [s, e], emit +1 at minute(s) and −1 at minute(e)+1. Concurrency at M is the running sum of all deltas up to M. Two rows per interval instead of seventy-eight. This is the sweep-line algorithm, applied to storage.

2.1 · Sharp edge one — the carry-in dependency

The running sum is defined from the beginning of time, not from the start of your query range. A dashboard asking for 18:00–19:00 that sums only the deltas inside that hour will miss every session that opened at 17:45 and is still watching. This is the classic delta-model undercount, and it is silent — the numbers look plausible, just low.

2.2 · Sharp edge two — peak is not summable

This is what the statement's 300K / 200K / 50K scenario is really pointing at, and it is the single most important constraint on the schema. Peak over a filtered set is not the sum of the per-dimension peaks, because different dimension slices peak at different minutes. Formally max(a+b) ≤ max(a)+max(b), and the gap is large in practice.

2.3 · Sharp edge three — never sum a distinct count

Session-level concurrency is summable across dimension buckets, because a session belongs to exactly one platform and one content. That is why deltas work at all. User-level concurrency is not — a user watching two contents simultaneously counts once, and summing per-content buckets double-counts them.

The repo already measured the consequence: a SummingMergeTree over uniqExact over-counted 9× (45,000 against a truth of 5,000). Distinct counts must travel as uniqExactState and be combined with uniqExactMerge, never summed.

Flaw 3a — the baseline uses approximate uniq

sql/10_intervals.sql defines cc_minute_stateless.active_state as AggregateFunction(uniq, String) and fills it with uniqState(). uniq is a HyperLogLog-family estimator with roughly 1–2% error.

Against a private, exact ground truth, that is a silent correctness bug on every number that passes through it. It must be uniqExact. The cost is memory proportional to distinct sessions per bucket — entirely affordable at minute grain, and non-negotiable when the score is exact-match.

2.4 · Average is time-weighted

Average concurrency over a range is the integral of the concurrency curve divided by the range length — equivalently, total_active_seconds / range_seconds. At uniform minute grain this degenerates to a plain mean, but only if you include the zero-concurrency minutes. At day grain rolled up from hours you must weight by bucket width. The active-seconds formulation is also an excellent independent cross-check, because it can be computed straight from interval durations without touching the delta layer at all. 

-- two independent routes to the same number; /reconcile should show them agreeing
-- route A — from the serving layer (integral of the staircase)
avg_concurrency = sum(concurrency_at_minute * 60) / range_seconds

-- route B — from the intervals directly (no delta layer involved)
avg_concurrency = sum(least(interval_end, B) - greatest(interval_start, A)) / range_seconds

3.4 · The premise the whole model rests on — MEASURED

AMENDED — does the heartbeat stop while backgrounded? Yes.

The gap model detects backgrounding only if the player stops emitting heartbeats when the app goes to background. If heartbeats continued in the background there would be no gap to detect, the gap model would report backgrounded users as watching, and it would fail the one thing the problem exists to test.

Run on the real 905,558-event file: 13,948 closed background→foreground pairs covering 3,301,211 s of backgrounded time contain 2,605 heartbeats — 0.047/min, against 4.72/min while active. A 100× drop; effectively zero. ADR 0001 stands. The query that answered it: 

-- for each background→foreground pair, how many heartbeats land strictly inside?
-- ≈0  → gaps work, ADR 0001 stands
-- ≈1/min → gaps are blind to backgrounding; bg/fg becomes load-bearing after all
WITH bg AS (
  SELECT video_session_id, event_timestamp AS t_bg,
         anyOrNull(event_timestamp) OVER (
           PARTITION BY video_session_id ORDER BY event_timestamp
           ROWS BETWEEN 1 FOLLOWING AND 1 FOLLOWING) AS t_fg
  FROM ev_raw
  WHERE event_type IN ('AppBackgrounded', 'AppForegrounded')
)
SELECT countIf(hb = 0) AS silent_pairs,
       countIf(hb > 0) AS noisy_pairs,
       avg(hb)              AS avg_beats_while_bg
FROM ( SELECT b.*, (
         SELECT count() FROM ev_raw h
         WHERE h.video_session_id = b.video_session_id
           AND h.event_type = 'VideoHeartbeat'
           AND h.event_timestamp > b.t_bg AND h.event_timestamp < b.t_fg ) AS hb
       FROM bg b WHERE t_fg IS NOT NULL )
SETTINGS log_comment = 'gate:hb-during-background';

A sibling unknown rode along: paused ≠ backgrounded. The statement excludes "backgrounded, paused, or silent" periods, but the sample file shows no pause events in the event_type census — they live in the under-explored event sub-column. That is the one that bit.

AMENDED — and heartbeats survive a pause. This one failed.

21,068 closed pause → resume pairs covering 3,002,604 s of paused time contain 37,854 heartbeats — 0.756/min, 16% of the active rate. That is one event every ~79 seconds, comfortably inside the 150s gap threshold, so a gap-only model never closes the interval and credits the entire pause as watching.

What those events are: video-resize (10,343), network-activity (8,338), buffer-health (6,835), plus scrubbing. None of it is playback progress. The player keeps reporting; the viewer is not watching.

The model is therefore a hybrid, and every "gap model" claim in this document is scoped accordingly: gaps for backgrounding and disappearance, explicit pause/resume windows subtracted for paused time. Shipped in sql/30_build_intervals.sql. The unresolved residue is the 23% of pauses that never resume — conservative (stays paused to end of run) vs permissive (ends at next event) differ by 99.3 h, 5.09% of counted watch time. Conservative is shipped; only the organisers can settle which the ground truth used.

04 — FLAWSThree things wrong with the baseline design

These are mechanical, not stylistic. Each one is a place where the documented design contradicts how ClickHouse actually executes, or where the arithmetic has a dependency nobody wrote down.

Flaw 1 · The compensating-delta mechanism cannot be implemented

docs/ARCHITECTURE.md says: "New heartbeats extend the interval (ReplacingMergeTree on interval_end) and emit a compensating delta. Nothing is rebuilt." Walk through what that requires at insert time and it comes apart.

A heartbeat arrives extending an interval from end E to E'. To keep the delta layer correct you must emit +1 @ minute(E)+1 and −1 @ minute(E')+1 — which requires knowing the previous end E. But a ClickHouse incremental materialized view is a trigger over the rows of the current insert block only. It has no memory of prior blocks and no access to the state of the target table. Learning E means reading session_intervals from inside the insert path — a read-modify-write that is racy under concurrent inserts and a well-known MV anti-pattern.

Flaw 2 · The carry-in and the peak rollup are both missing

Figure 4 covered the carry-in. The sibling problem is that peak does not roll up over time either, not just over dimensions. Peak-over-a-day is max() across 1,440 minute-values, so every day-grain peak query is forced down to minute grain — 1,440 rows per dimension combination, per query. The baseline has cc_minute_delta and nothing coarser, so there is no cheap path for the hour- and day-grain queries the benchmark set explicitly includes.

Flaw 3 · Three correctness leaks

05 — EVOLUTIONSFour changes that fix all three

E1 · Split intervals at hour boundaries

One trick removes the carry-in dependency and makes peak pre-aggregable. When emitting deltas, clip every active interval to the hour: for each hour an interval touches, emit a +1 at its start within that hour, and a −1 only if it actually ends within that hour. If it survives past the hour, emit no close — the next hour re-opens it with a fresh +1. 

-- emission rule: clip the close to the hour; omit it if the interval survives the hour
SELECT
    h                                                   AS hour_bucket,
    greatest(toStartOfMinute(interval_start), h)      AS open_minute,
    if(interval_end < h + INTERVAL 1 HOUR,
       toStartOfMinute(interval_end) + INTERVAL 1 MINUTE,
       NULL)                                            AS close_minute  -- NULL ⇒ no −1 emitted
FROM session_intervals
ARRAY JOIN arrayMap(i -> toStartOfHour(interval_start) + toIntervalHour(i),
              range(toUInt32(dateDiff('hour', toStartOfHour(interval_start),
                                          toStartOfHour(interval_end)) + 1))) AS h

The payoff — peak becomes summable over time

Because each hour is now self-contained, we can pre-aggregate per (dims, hour): store the max of that hour's running sum and its integral (concurrency-seconds). Then peak over any hour-aligned range is the max of the stored maxes, and average is sum(integrals) / range_seconds — correctly time-weighted, zero-minutes included for free.

E2 · Replace compensating deltas with a two-tier lambda

The insight that unlocks this: for the hot tail there is a delta-free representation that is fully streamable and idempotent. Each heartbeat at time t grants a lease [t, t + LEASE) where LEASE = HEARTBEAT_GAP_S. A session is active in minute M if and only if some lease covers M. An MV arrayJoins each heartbeat into the 3–4 minute buckets its lease covers (AMENDED — 3 or 4, not exactly 3; the count depends on the beat's offset within its minute) and accumulates uniqExactState(video_session_id).

AMENDED — E2's hot tier is BLOCKED. Two corrections, one of them fatal as specified.

(a) The volume arithmetic is wrong. The fan-out below was derived as "3 buckets, because a 60s cadence with a 150s lease covers 3". There is no cadence. Per beat the fan-out is 3–4; per active session-minute it is ≈ 4.72 × 3.5 ≈ 16 rows, where a one-beat-per-minute model predicted 3 — a 5× under-estimate of hot-tier write amplification. And because p50 inter-arrival is 0s, most of those rows are redundant insertions of the same session id into the same uniqExact state. uniqExact absorbs them correctly — the cost is insert and merge work, not cardinality error — but the TTL window must be sized from 16 rows/session-minute, not 3. DERIVED from the ADR 0007 measurement.

(b) The lease model inherits the pause bug. Leases renew through a pause, because heartbeats keep arriving at 0.756/min — one every ~79s, inside LEASE = 150s. So coverage never breaks and the hot tier as specified counts paused time as watching. The equivalence argument in Figure 9 is what hides it: the lease model is provably equivalent to the gap-only model — and the gap-only model is exactly the one §3.4 discarded. Equivalence to a discarded model is not a correctness argument.

sql/30_build_intervals.sql fixed this for the sealed tier only. Upper bound on the exposure: 3,002,604 s (834 h) of measured closed-pause time against 1,949.3 h of counted watch time — the same order as the answer. A corrected lease model must either (1) let a pause truncate a live lease and grant none until resume (correct, but "is this session paused?" is cross-block state, which is the read-modify-write E2 exists to avoid); (2) emit suppressing rows, which uniqExact cannot subtract, so the tier would have to move to sum-of-deltas and lose its idempotence; or (3) keep leases exactly as written and relabel the hot tier the session-independent upper bound — one of the two models the statement mandates comparing — with the sealed tier, not the hot tier, answering the benchmark. Option 3 is the only one that is free. Tracked in docs/adr/0005-heartbeat-lease-semantics.md §Amendment; [H5] is gated on it.

E3 · Stragglers beyond the watermark — correction by deterministic diff

One case E2 does not cover: a heartbeat arriving older than the sealed watermark. Because derivation is deterministic and ev_raw retains everything, the fix needs no state at all — recompute the affected session's deltas with and without the straggler, and append the difference. SimpleAggregateFunction(sum, Int64) absorbs negative corrective rows natively.

E4 · Serving-key hedges for the filter matrix

Two cheap fixes for gaps in the filter story. First, video_type is a named business dimension but lives behind a content_id → dictGet, which turns a video-type filter into a several-thousand-id IN list with poor prefix pruning — materialise it into the serving tables instead (cardinality ~4, nearly free in the key). Second, add a PROJECTION reordered (content_id, minute) for content-first queries that skip the platform prefix.

A third hedge, forced by ADR 0002 — and anticipated by it

ev_raw is ordered (toStartOfHour(event_timestamp), platform, video_session_id, event_timestamp) — a measured 17.3× better on the dashboard shape than leading with the session id. But the E2 finalizer and the E3 correction path are both point lookups by video_session_id, which is now third in the key rather than first.

ADR 0002 called this exact case in advance: "if a 'single session lookup' access pattern ever becomes hot, add a PROJECTION ordered by video_session_id rather than reverting the key." This design is what makes it hot. So: add the projection at H4 and measure it — do not revert ADR 0002, whose win is on the access pattern that runs orders of magnitude more often. Until the projection exists, the finalizer's per-session read cost is the largest unmeasured quantity in the evolved design.
