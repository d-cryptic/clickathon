WHAT IS BEING SCALED
  N x the AUDIENCE inside the SAME 99-hour window: N x as many sessions,
  drawn from the same session-start-MINUTE histogram, so peak CONCURRENCY
  is itself N x.
  That is what "100x" means for this problem. Scaling the calendar is the
  easy axis — an extra day is an extra partition and prunes away. Scaling
  the audience is what stresses the per-session arrays in the derivation,
  the uniqExact states in the stateless tier, and delta cardinality.

  Generated server-side by tools/scale-load.sql (INSERT ... SELECT FROM
  numbers_mt). Every draw is cityHash64(session, salt), so a scale is
  reproducible byte-for-byte from (S, SEED).
--------------------------------------------------------------------------
WHY THIS RUN EXISTS — re-measured after ADR 0016 (2026-08-01)
  The previous run (2026-08-01T15:18Z, commit 8af15cb) measured the
  pre-ADR-0016 model: three build stages, and NO user tier at all — its
  scratch databases never instantiated cc_user_minute. ADR 0016 changed
  real things underneath those numbers:
    * cc_user_minute: AggregatingMergeTree + mv_user_minute (set union)
      -> ReplacingMergeTree(computed_at) + explicit backfill INSERT.
      Different engine, different merge behaviour, different read cost.
    * retraction is an explicit empty-state row at a newer version, so
      corrected buckets become ROWS, not absences — row counts only grow.
    * the publisher gained 'hours' and 'users' phases: a publish run does
      strictly more work than the run whose timings were published.
  So this run builds all four tiers, reconciles the user tier against the
  interval expansion at every scale, and times a one-straggler publish
  (all six phases) at every scale. A frozen copy of the pre-ADR-0016
  headline figures is printed at the end for the diff.
