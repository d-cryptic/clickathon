==========================================================================
2  DETERMINISM — the same query at max_threads 1, 8 and 32
==========================================================================

Method: each query is emitted as a FULL ORDERED RESULT SET and fingerprinted
with md5 — not an order-independent hash-sum, because a hash-sum can cancel
compensating errors and cannot be diffed. Nine runs per object: threads
1 / 8 / 32, three repetitions each. All nine run with

    --max_block_size 1024 --group_by_two_level_threshold 1
    --group_by_two_level_threshold_bytes 1

which forces the two-level parallel GROUP BY at every scale, i.e. the state
merging that a bare argMax's tie handling actually depends on. Without those
settings the defect below is much harder to provoke, which is precisely why
it survived until a low-traffic holdout day surfaced it.

==========================================================================
4  WHY THE TUPLE IS SUFFICIENT
==========================================================================

argMax keeps the row with the maximal second argument and, among equals, keeps
whichever partial state its merge happened to visit first — which under a
two-level parallel GROUP BY is a function of thread scheduling.

    (concurrent, -toInt64(toUInt32(minute)))

is a TOTAL order on the candidate rows: two rows can share `concurrent`, but no
two rows in a group share a minute, so no two tuples are equal and "among
equals" never arises. Nothing is left for merge order to decide. That is why
the result does not move with max_threads and cannot move with part count,
merge state or insert order either.

The negation must be applied to a SIGNED type. `-toUInt32(minute)` would wrap
to a huge unsigned value and invert the comparison, i.e. select the LATEST
minute while looking like it selects the earliest; hence
`-toInt64(toUInt32(minute))` everywhere, with no exceptions.
