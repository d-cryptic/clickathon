================================================================================
DEDUPLICATE LATE OR REPEATED EVENTS — investigation and verdict
Step 3 of the pipeline in docs/upstream/README_START_HERE.md:
  "Apply foreground-only filtering and deduplicate late or repeated events."

Target: ClickHouse Cloud, database `sonyliv`, 2026-08-01.
All numbers below were produced by queries against the loaded data. Nothing here
is hand-computed.

--------------------------------------------------------------------------------
VERDICT
--------------------------------------------------------------------------------
The 4,210 duplicate rows are PROVABLY INERT for concurrency. Deduplicating
ev_raw changes NOTHING: not one interval, not one minute, not the peak, not the
integral. We therefore DO NOT add a dedup step to the pipeline.

  *** SCOPE OF THIS VERDICT — added 2026-08-01, after re-measurement ***
  This proof was taken against the model generation that served THREE dimensions
  (platform, country, content_id) at the old headline (30,769 intervals, peak
  2,887 @ 10:56). At that grain it holds, and the boundary/total half of it
  still holds verbatim on the current model (section 6). What did NOT survive
  is the DIMENSION grain: the model now serves SEVEN dimensions attributed by a
  frequency vote (ADR 0008/0009), which is exactly the multiplicity-sensitive
  aggregate guard (a) in section 5 warns about. The guard fired. Re-measured on
  the current model (30,323 intervals, peak 2,917): duplicates remain inert for
  every interval boundary, every total and the unfiltered curve, and are NOT
  inert for dimension attribution — 6 intervals flip audio_language and the
  per-language curves move. Full numbers in section 6; the mentor dossier is
  doubts/06-dedup-at-filter-grain.md. Read "INERT" below as "inert at total
  grain"; do not cite this file for dimension-filtered answers.

That is a deliberate answer, not an omission. A dedup pass would cost a full
extra pass over ev_raw on every rebuild and would buy exactly zero correctness.
The reason it buys zero is structural, and the structure is what we rely on —
so the argument is spelled out below rather than asserted, and the guard that
protects it is named at the end.

================================================================================
2 · WHY THEY ARE INERT — the mechanism
================================================================================
sql/30_build_intervals.sql reduces each session to five things. A duplicated row
is, by definition, a repeat of a (timestamp, event_type, event) that is already
present. Take each consumer in turn:

  ts = arraySort(groupArray(timestamp))
      A duplicate adds a REPEATED value to a sorted array. The run split is
      arraySplit((t,i) -> (i>1) AND (t - ts[i-1]) > 150, ...). For the repeated
      element the difference is 0, and 0 > 150 is false, so a duplicate can
      never open a new run. Run boundaries are read as run[1] and
      run[length(run)] — the min and max of the run — which are unchanged by
      repeats. The runs are therefore IDENTICAL, element multiplicity aside.

      Demonstrated directly:
        ts_clean = [100,160,220,400,460]
        ts_dup   = [100,160,220,220,400,460,460]
        runs_clean = [[100,160,220],[400,460]]
        runs_dup   = [[100,160,220,220],[400,460,460]]
        bounds     = [(100,220),(400,460)]  for BOTH        -> identical

  pauses / resumes
      A duplicated `pause` yields a duplicated pause WINDOW (p, first_resume>p),
      because arrayFirst over `resumes` returns the first match and duplicate
      resumes do not change which value is first. The complement fold is
        (acc, win) -> (if(win.1 > acc.2, push (acc.2, win.1)), greatest(acc.2, win.2))
      On the second identical window, acc.2 already equals that window's end,
      which is > its start, so the push is skipped and the cursor does not move.
      The fold is IDEMPOTENT under repeated identical windows.

  is_open = countIf(event_type = 'VideoSessionEnd') = 0
      A zero-test. Duplicates can only increase a count, never create the first
      occurrence, so they cannot flip 0 -> non-zero or non-zero -> 0.

  any(user_id) / any(content_id) / any(platform) / any(country)
      A duplicate is a copy of a row that remains after dedup, so the SET of
      candidate values per session is unchanged and any() draws from an
      identical domain. (any() is non-deterministic across runs regardless of
      duplicates; the A/B in section 3 pins it to min() on BOTH sides so the
      experiment isolates dedup as the only variable.)

Because session_intervals is unchanged, EVERY downstream tier is unchanged by
construction: cc_minute_delta is a pure function of session_intervals, and
cc_hour_agg is a pure function of cc_minute_delta. Proving interval equality
proves the whole serving layer.

================================================================================
4 · WHY THIS IS THE RIGHT ANSWER, NOT A SHORTCUT
================================================================================
The interval model is INSENSITIVE TO EVENT MULTIPLICITY BY DESIGN. It reads a
session's event stream as a SET of instants and asks two questions of it —
"where are the gaps longer than 150s" and "which windows are paused" — and both
are functions of the set, not of the multiset. Idempotence under replay is
therefore a property of the model, not a lucky property of this file.

That matters far more than the 4,210 rows do, because it is the same property
that makes the pipeline safe against the arrival classes docs/ARCHITECTURE.md
has to absorb on the unseen day:

  - a replayed ingest batch          -> no-op
  - an at-least-once delivery retry  -> no-op
  - a late heartbeat already seen    -> no-op

A dedup step would add a full pass over ev_raw per rebuild to defend a property
the model already has. The honest engineering answer is to state the invariant,
prove it, and guard it — which is what this file does.

Note also that ev_raw is already declared with
`non_replicated_deduplication_window = 1000` (sql/00_schema.sql), which makes a
re-INSERT of an identical BLOCK idempotent. That is block-level insert dedup and
is a different mechanism from row-level dedup; it does not remove these 4,210
rows (they arrived inside the original load), and it is not what makes them
inert. Do not conflate the two.

================================================================================
5 · WHEN THIS VERDICT STOPS HOLDING — the guard
================================================================================
The inertness argument depends on three things. If any changes, re-run the A/B
in section 3 before trusting concurrency again.

  (a) THE MODEL STAYS MULTIPLICITY-INSENSITIVE.
      Any aggregate over ev_raw that COUNTS events rather than reading their
      timestamps as a set breaks immediately. Concretely: count(), a
      heartbeat-rate or inter-arrival statistic, an events-per-minute quality
      metric, or a "session is active if it emitted >= N beats" rule would all
      be inflated by up to 6x on the affected sessions. ADR 0007's measured
      inter-arrival p99 of 49s — the number GAP_S=150 is derived from — is
      exactly such a statistic. It was computed on data containing these
      duplicates, and duplicates only ever SHRINK an inter-arrival gap, so the
      true p99 is >= 49s and GAP_S=150 remains conservative. Recompute it on
      deduplicated input if that threshold is ever retuned.

  (b) subtitle_language DOES NOT BECOME A DIMENSION.
      The single non-identical duplicate group (section 1) differs only in that
      column. Today it is inert because the model does not read it. Add it as a
      filter dimension and that one session becomes order-dependent: any()
      would pick 'UNK' or 'OFF' non-deterministically and the session would land
      in a different bucket across rebuilds. If subtitle_language is ever
      promoted, dedup must become deterministic — pick a winner explicitly, e.g.
      `LIMIT 1 BY key ORDER BY subtitle_language`, and record the tie-break.

  (c) THE UNSEEN DAY LOOKS LIKE THIS ONE.
      0.46% duplicates, max 6 copies, all within-session. A qualitatively
      different corruption — the SAME (session, timestamp) carrying a DIFFERENT
      content_id or platform, which does not occur here — would make any()
      order-dependent and would need a deterministic tie-break rather than a
      no-op. The one-line detector for that case:

        SELECT count() FROM (
          SELECT video_session_id
          FROM ev_raw
          GROUP BY video_session_id, event_timestamp, event_type, event
          HAVING uniqExact((content_id, platform, country, user_id)) > 1);

      This returns 0 on the provided file. If it returns non-zero on the unseen
      day, the verdict in this file does not transfer — add the deterministic
      dedup and re-run the section 3 A/B.

6 · RE-MEASUREMENT AT SEVEN-DIMENSION GRAIN — 2026-08-01, current model
================================================================================
The model this file originally measured attributed three dimensions per session
with any(). The current model (ADR 0008/0009/0012; 30,323 intervals, 1,978.1 h,
peak 2,917) attributes SEVEN dimensions per interval with a dominant-value vote:

  arraySort(v -> (-countEqual(values, v), v), arrayDistinct(values))[1]

countEqual counts EVENTS — the aggregate class guard (a) names. The section 3
A/B was therefore re-run against the current derivation, verbatim from
sql/30_build_intervals.sql, both arms in one query. The dedup arm is pinned
deterministically so the arms are comparable:

  SELECT * FROM ev_raw
  ORDER BY video_session_id, event_timestamp, event_type, event, subtitle_language
  LIMIT 1 BY video_session_id, event_timestamp, event_type, event
  -- 905,558 -> 901,348 rows

WHAT STILL HOLDS (the set-of-instants argument, unchanged):

  intervals_raw / intervals_dedup       30,323 / 30,323
  hours_raw / hours_dedup               1,978.1 / 1,978.1
  cityHash64 of all (session, start, end), both arms
                                        1595692701993512111  <-- IDENTICAL
  => unfiltered curve, peak 2,917 and integral unchanged BY CONSTRUCTION.

WHAT DOES NOT HOLD — dimension attribution is a vote, and duplicates vote:

  intervals whose 7-dimension attribution differs        6
    (all audio_language; all among hin / non / unk)
  session 3575B56C… interval 10:52:15-10:52:43, the mechanism:
    raw   votes  unk 11, hin 5   -> unk
    dedup votes  unk  5, hin 5   -> tie -> tie-break by value -> hin
    (six duplicated unk-carrying heartbeats WERE the majority)

  serving-convention per-minute curves by audio_language:
    value   minutes_differing   max_abs_diff   peak_raw   peak_dedup
    hin            18                2           1,774        1,774
    non            15                1              30           30

    unfiltered      0                0           2,917        2,917

VERDICT AT THIS GRAIN: NOT INERT. Upstream step 3 ("deduplicate late or
repeated events") is validated as a no-op for totals and NOT validated for
dimension-filtered answers. sql/90_reconcile.sql compares per-minute totals
only and carries no dimension columns, so no gate we run can see this class of
difference. Whether the raw or deduplicated attribution is the one to serve is
a graders' definition question: doubts/06-dedup-at-filter-grain.md carries the
evidence, the exact wording, and the decision table. Policy ADR 0016 is
reserved for recording the answer.
