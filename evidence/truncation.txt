ROOT CAUSE — session_intervals is NOT identical to a clean rebuild
--------------------------------------------------------------------------
Row 1:
──────
incremental_intervals: 30323
control_intervals:     30323
interval_end_mismatch: 301
is_open_mismatch:      300
incremental_TOO_LONG:  301
incremental_too_short: 0
max_excess_seconds:    60

  The keys match exactly — no interval is missing or extra. What differs is the
  VERSION RESOLUTION. session_intervals is ReplacingMergeTree(interval_end), which
  keeps the row with the LARGEST interval_end. sql/10_intervals.sql justifies that
  with 'late heartbeats EXTEND an interval', i.e. it assumes re-derivation is
  monotonically increasing. Truncation falsifies the assumption: the provisional
  row carries TAIL_S=60s of grace because its run appeared to end, and the completed
  derivation places the true end EARLIER — at a pause, or at a real VideoSessionEnd
  inside the grace window. The stale longer row then outranks the correct one
  permanently, and drags a stale is_open=1 with it.

  worked examples:

SECOND FINDING — starts/ends cannot carry the ADR 0006 negative correction
--------------------------------------------------------------------------
  cc_minute_delta.starts/ends are SimpleAggregateFunction(sum, UInt64). ADR 0006
  step 3 says to append 'the NEGATION of the deltas for the old derivation'. For
  delta (Int64) that is exact — proven above. For an unsigned column it is not
  representable, and ClickHouse does not reject it; it wraps, silently:
   ┌─stored_row─┐
1. │       -100 │
2. │        100 │
   └────────────┘
  sum() = 0  (correct, but only because UInt64 sum wraps modulo 2^64)   max() = 100  <- nonsense

  This run sidesteps it by zeroing starts/ends on the corrective row, which
  leaves the counters permanently inflated:
Row 1:
──────
incremental_starts: 24378
control_starts:     20002
incremental_ends:   21190
control_ends:       16826
  Remedy: make both SimpleAggregateFunction(sum, Int64), like delta.

WATERMARK — how wide must W be? (measured; ADR 0004 requires it be set from data)
--------------------------------------------------------------------------
  (a) truncation damage — how far BACK from the cut the stump was wrong:
      earliest corrupted minute 2026-07-26 10:55:00 = 60 s before the cut · 3 minutes wrong
  (b) model revision horizon — an interval stays revisable for GAP_S + TAIL_S:
      150 + 60 = 210 s after its last observed event.
  (c) straggler lag — events arriving after their own VideoSessionEnd (ADR 0007):
Row 1:
──────
sessions_with_post_end_events: 239
pct_of_sessions:               2.2
p999_lag_s:                    733
max_lag_s:                     2081

  W = max(210, 2081) rounded up = 2400 s (40 min).
  The binding constraint is the straggler tail, not truncation: a clean cut only
  damages the last 60 s, but a single event 2081 s late reopens a minute that far
  back. W=2400 leaves ~15% headroom over the observed maximum. Minutes newer than
  W are served by the hot tier (ADR 0004); anything older than W that still moves
  goes down the correction-by-diff path, which this run proves is exact.

VERDICT
--------------------------------------------------------------------------
  1. The from-scratch build in an isolated database reproduces production exactly
     (2887 @ 10:56, 2450 @ 11:10) — the derivation is deterministic.
  2. This test is TWO-SIDED, so read both halves before concluding anything.
     sql/70 deliberately KEEPS a ReplacingMergeTree(interval_end) variant to
     reproduce the historical defect. On that variant absorption still DIVERGES —
     3 of 1578 minutes, overcounting the PEAK by 37 (2924 vs 2887). That is the
     test proving it can still DETECT the bug, not a report that we have it.
  3. On the build_version variant — which is what sonyliv runs today — absorption
     CONVERGES on all 1578 minutes, row for row against the clean rebuild, peak 2887.
  4. Root cause, for the record: versioning on interval_end assumes re-derivation
     only ever EXTENDS an interval. It does not — a provisional interval carries
     60s of tail grace and the completed derivation can place the true end EARLIER,
     so the stale longer row outranked the correct one permanently.
  5. cc_minute_delta.starts/ends are Int64. As UInt64 they silently WRAPPED when
     ADR 0006 negated a corrective row — sum() stayed right by modular arithmetic
     so the bug hid, while max() returned 1.8e19.
  6. Watermark W = 2400 s, set by the 2081 s straggler tail, not by truncation.

  Both schema fixes are APPLIED to sonyliv (commit 388a845) and the reconcile
  gate passes against them. This test is now a regression guard, not a bug report:
    sql/10_intervals.sql  session_intervals  ReplacingMergeTree(build_version)
    sql/10_intervals.sql  cc_minute_delta    starts/ends SimpleAggregateFunction(sum, Int64)
