  WALKTHROUGH §5 records proj_by_session as measured and NOT shipped: 27.7x on
  a single-session lookup, but "the actual straggler path uses IN (subquery),
  which full-scans anyway, so the real gain is 1.00x for +94% storage".
  The finalizer's derive is exactly that IN (subquery) — plus an event-time
  window — so the shape is worth re-measuring rather than inheriting.

  Compare against the PHASE 5 table above: the projection IS chosen for the
  IN (subquery) shape on 26.2. This does not overturn the storage trade — that
  is still the operator's call — but the '1.00x' half of it does not hold for
  the finalizer's query. ADR 0013 records both numbers and ships neither.
  NOTE: sql/60_projection.sql hard-codes 'sonyliv.', so it cannot be applied to
  any other database; this phase had to issue the ALTER itself. Same class of
  defect ADR 0010 fixed in sql/80_content.sql.
