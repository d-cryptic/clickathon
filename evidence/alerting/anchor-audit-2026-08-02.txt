DECLINE-ALERT THRESHOLDS — ARE THEY SEMANTICALLY ANCHORED?
================================================================================
Measured 2026-08-02, read-only against the graded `sonyliv` database
(ClickHouse Cloud 26.2.1.525). SELECTs only. Script: the six probes below.

WHAT WAS CLAIMED
--------------------------------------------------------------------------------
docs/DECLINE_ALERTING.md said, of the OUTAGE feature `hb_per_session < 1.0`:

  "ADR 0007 measured 4.72/min while actively watching, 0.756/min while paused,
   0.047/min while backgrounded. So a threshold of 1.0 sits above the fully-
   paused rate: tripping it means the fleet is quieter than it would be if every
   remaining viewer had hit pause, which no viewer behaviour explains."

and of `end_coverage`:

  "It is a ratio whose meaning fixes its own thresholds: 1.0 = every departure
   accounted for, 0.0 = sessions vanished without closing."

VERDICT: the first claim is FALSE — the inequality is stated backwards, and the
two quantities are from different populations. The second is FALSE — the ratio
exceeds 1.0 on 81 minutes of the delivered file and reaches 3.0, so it is not a
share and 1.0 does not mean "all departures explained". Codex 005 §4.1 is
confirmed on both counts, by independent measurement.

--------------------------------------------------------------------------------
PROBE 1 — ADR 0007's rates, re-derived live.  BOTH REPRODUCE EXACTLY.
--------------------------------------------------------------------------------
  state          pairs      secs    beats   per_min
  backgrounded   13948   3301211     2605     0.047
  paused         21068   3002604    37854     0.756

These are heartbeats per SESSION-MINUTE OF THAT STATE — beats strictly inside
each closed bg->fg / pause->resume pair, over the duration of those pairs. The
ADR is sound and its numbers are good.

  (Aside on the 4.72 "active" figure: it is beats per NAIVE-SPAN minute —
   843,600 / 178,614 = 4.72. Per COUNTED-ACTIVE minute the same file reads
   843,600 / 118,686 = 7.11. Both correct; the rate depends on the denominator
   you pick, which is exactly the trap the OUTAGE anchor fell into.)

--------------------------------------------------------------------------------
PROBE 2 — WHY THE ANCHOR FAILS. Two independent reasons.
--------------------------------------------------------------------------------
(a) THE INEQUALITY IS BACKWARDS.

    trip condition          hb_per_session < 1.0
    fully-paused reference  0.756
    0.756 < 1.0             -> THE FULLY-PAUSED FLEET SATISFIES THE TRIP
                               CONDITION.

    So tripping the threshold does NOT mean "quieter than if every viewer had
    paused". A fleet that is merely, entirely paused already trips it. For the
    sentence to be true the threshold must sit BELOW 0.756, not above it.
    "1.0 sits above the fully-paused rate" is arithmetically true and is the
    opposite of what the argument needs.

(b) THE TWO NUMBERS ARE NOT COMPARABLE ANYWAY.

    ADR 0007's 0.756  =  beats inside pause windows / paused session-minutes
    the alert's ratio =  ALL VideoHeartbeat rows in a wall-clock minute
                         / ACTIVE concurrency from v_cc_minute_series_total

    The numerator counts every session's beats, including paused and
    backgrounded ones. The denominator counts only active viewers, which by
    construction EXCLUDES the paused. They are different populations, so no
    threshold on the second can be justified by a rate measured on the first.

    Worse, the hypothetical is not even representable: if every remaining viewer
    paused, active concurrency -> 0, `greatest(concurrent,1)` floors the
    denominator at 1, and the ratio reads HIGH, not low. The scenario the
    anchor invokes cannot produce the reading the anchor predicts.

--------------------------------------------------------------------------------
PROBE 3 — the classifier, reproduced verbatim on every firing minute
--------------------------------------------------------------------------------
  class    minutes  hb_min  hb_max  cov_min  cov_max
  ENDING        17   3.248   6.095    0.917    1.703
  OUTAGE        11   0.000   0.071    0.000    0.035

Matches Codex 005 exactly. The 28 firing minutes and the separation are real —
what is wrong is the STORY about where the number 1.0 came from, not the number's
ability to split these two populations.

--------------------------------------------------------------------------------
PROBE 4 — is end_coverage a share?  NO.
--------------------------------------------------------------------------------
  minutes  above_one  max_cov  pct_above_one
     6195         81      3.0           1.31

A share cannot exceed 1.0; this reaches 3.0. So "1.0 = every departure
accounted for" is not what the number means. Two mechanisms, both measured:

  - the numerator counts RAW VideoSessionEnd rows, and 14 sessions emit more
    than one (probe 5);
  - the denominator is MODELLED net concurrency loss plus starts, whose minute
    is tail-adjusted and does not line up with the raw end event's minute.

PROBE 6 — can NORMAL behaviour trip the OUTAGE heartbeat test?
--------------------------------------------------------------------------------
Over every minute where heartbeats were still arriving (ingestion demonstrably
alive):

  minutes_with_beats  also_below_1.0  also_below_0.756
                3816               3                 3

Only 3 minutes of 3,816 read below 1.0, and the same 3 read below 0.756 — they
are in the truncation tail, not normal behaviour. So NO normal-behaviour false
positive is demonstrated on this file, in either direction. The threshold is not
shown to be unsafe; it is shown to be UNJUSTIFIED BY THE STATED ARGUMENT.

--------------------------------------------------------------------------------
PROBE 7 — would an ANCHORED threshold change any verdict?  NO. THE FIX IS FREE.
--------------------------------------------------------------------------------
  outage@1.00  outage@0.756  outage@0.50  outage@0.25  ending (unchanged)
           11            11           11           11                  17

Every threshold from 1.00 down to 0.25 classifies the delivered file
identically, because the observed gap is enormous: 0.071 (worst outage minute)
against 3.248 (best ending minute), a factor of 46.

CONSEQUENCE. Moving the shipped threshold to 0.5 would cost nothing on this file
and would make the sentence "quieter than a fully-paused fleet" true of the
numerator's rate — though (b) above means the anchor would still be directional
rather than exact, because the denominator is a different population.

NOT APPLIED HERE. tools/clickstack-alerts.sh is not owned by this task. The doc
has been corrected to describe what is actually shipped — a threshold fitted to
a 46x gap, labelled as fitted — and the change is recorded as a recommendation.

--------------------------------------------------------------------------------
BOTTOM LINE
--------------------------------------------------------------------------------
The detector and the classifier work on this file, and the margins are wide.
Neither threshold is derived from measured semantics the way the document
claimed. A fitted threshold with a 46x margin, openly labelled, is defensible.
Describing it as principled when it is not is the thing that fails review — and
this claim was repeated in a merge commit without being checked, which is how it
survived this long.
